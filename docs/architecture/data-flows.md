# Потоки данных и семантика доставки

Версия 0.1 · Шаг плана 0.3 · Статус: черновик

Детализация раздела 3.2 плана. Для каждого потока определены производитель, потребители, ключ, порядок, семантика, механизм идемпотентности и поведение при сбое. Решения по семантике закрепляются в ADR-006, по партиционированию - в ADR-007. Число партиций и масштабирование - в [scaling.md](scaling.md).

---

## 1. Общие настройки клиентов Kafka

| Параметр | Значение | Зачем |
|---|---|---|
| Продюсер `acks` | `all` | Запись подтверждена всеми синхронными репликами |
| Продюсер `enable.idempotence` | `true` | Нет дубликатов из-за повторов продюсера внутри сессии |
| Продюсер `compression.type` | `zstd` | Объём хранения и сети ([scaling.md](scaling.md#5-сайзинг)) |
| Продюсер `linger.ms` | 2-5 (горячий путь), 20 (остальные) | Баланс задержки и размера пакета |
| Топик `replication.factor` / `min.insync.replicas` | 3 / 2 в кластере; 1 / 1 на одной машине | RPO = 0 в кластере при отказе одного брокера |
| `unclean.leader.election.enable` | `false` | Не терять подтверждённые записи |
| Потребитель `enable.auto.commit` | `false` | Смещение фиксируется только после обработки |
| Потребитель `isolation.level` | `read_committed` | Не видеть незавершённые транзакции |
| Потребитель `partition.assignment.strategy` | `cooperative-sticky` | Ребалансировка без остановки всех партиций |
| Потребитель `group.instance.id` | Задан (статическое членство) | Перезапуск экземпляра без ребалансировки в пределах `session.timeout.ms` |
| `session.timeout.ms` | 10 000 | Обнаружение отказа экземпляра ≤ 10 с (входит в RTO) |

## 2. Классы семантики

| Класс | Механизм | Где применяется |
|---|---|---|
| **EOS-K** - exactly-once внутри Kafka | Транзакция «чтение - обработка - запись»: выходные сообщения, изменения changelog и смещения входа фиксируются атомарно | Normalizer, Correlation Engine |
| **EOS-DB** - эффективно exactly-once на границе с PostgreSQL | Inbox: запись идентификатора входного сообщения в той же транзакции БД, что и изменение агрегата; смещение фиксируется после коммита БД; повтор отбрасывается по inbox | Incident Service, Response Engine, Command Service, Audit Service |
| **Outbox** | Событие записывается в таблицу outbox в транзакции изменения агрегата; реле публикует его в Kafka и помечает отправленным. Возможна повторная публикация после сбоя реле; потребители идемпотентны | Все сервисы с PostgreSQL |
| **ALO+ID** - at-least-once с идемпотентностью по идентификатору | Повторы возможны, потребитель отбрасывает их по идентификатору или по версии агрегата | Ввод, команды, аудит, проекции |

Выбор EOS-K для Normalizer расходится с планом (там указано at-least-once с идемпотентностью по `event_id`). Причина: дубликаты в `psim.events.normalized.v1` искажают пороговые правила корреляции, а устранять их ниже по потоку пришлось бы с горизонтом в минуты при 50 000 событий/с. Транзакции переносят дедупликацию в одно место с малым состоянием (трекер порядковых номеров источников). Запасной вариант на случай, если замер в ходячем скелете покажет превышение бюджета 30 мс, - at-least-once с дедупликацией в Correlation Engine с коротким горизонтом. Решение фиксируется в ADR-006.

## 3. Потоки

### 3.1 Ввод: коннектор -> `psim.ingest.raw.v1`

| Свойство | Значение |
|---|---|
| Производитель | Connector Gateway |
| Потребители | Normalizer (группа `psim-normalizer`) |
| Ключ | `source_id` |
| Порядок | В пределах источника - в порядке отправки SDK |
| Семантика | ALO+ID: коннектор получает подтверждение пакета только после `acks=all` (CS2); неподтверждённое SDK досылает из буфера на диске |
| Идемпотентность | `event_id` и `(source_id, source_epoch, source_seq)`; дубликаты отсекает Normalizer |
| Retention | 6 ч по умолчанию; минимум - время восстановления Normalizer с запасом |

**Поведение при сбоях:**

| Сбой | Поведение |
|---|---|
| Падение шлюза до записи в Kafka | Пакет не подтверждён; SDK переподключается к другому экземпляру и досылает |
| Падение шлюза после записи, до подтверждения | SDK досылает; в топике появляется дубликат; Normalizer отбрасывает его по трекеру |
| Kafka недоступна или медленная | Шлюз перестаёт выдавать кредиты; SDK буферизует на диске; при заполнении буфера SDK генерирует `system.connector.buffer_overflow` и применяет политику вытеснения (по умолчанию - отбрасывать `info`, сохранять остальное) |
| Невалидное сообщение | Отклоняется шлюзом с кодом ошибки, в Kafka не попадает; учитывается в метриках коннектора |

### 3.2 Нормализация: `psim.ingest.raw.v1` -> `psim.events.normalized.v1`

| Свойство | Значение |
|---|---|
| Производитель | Normalizer |
| Потребители | Correlation Engine (`psim-correlation`), Event History (`psim-event-history`), Projection Service (`psim-projection`, только классы `alarm`, `fault`, `restore`, `state`) |
| Ключ | `site_id + ":" + zone_id` |
| Порядок | В пределах зоны; порядок источника сохраняется, так как источник принадлежит одной зоне |
| Семантика | EOS-K |
| Состояние | Трекер источников: для `(source_id, source_epoch)` - максимальный номер и битовая карта последних 4096 номеров. Хранится в памяти и в compacted-топике `psim.normalizer.state.v1` в той же транзакции |
| Идемпотентность | Повтор с известным номером отбрасывается; разрыв номеров порождает `system.source.sequence_gap` |
| Retention | 24 ч по умолчанию; настраивается ([scaling.md](scaling.md#52-оценка-при-50-000-событийс)) |

**Смена зоны устройства.** При `DeviceMoved` события устройства начинают попадать в партицию новой зоны. Порядок между событиями до и после переноса не гарантируется; правила корреляции работают по event time и это допускают.

**Поведение при сбоях:**

| Сбой | Поведение |
|---|---|
| Падение экземпляра | Транзакция прерывается; новый владелец партиции восстанавливает трекер из `psim.normalizer.state.v1` и продолжает с зафиксированного смещения; дубликатов нет |
| Нет устройства или правила отображения | Сообщение уходит в `psim.dlq.normalizer.v1` в той же транзакции |
| Устаревшая копия каталога | Нормализация продолжается по текущей копии; каталог догоняет ≤ 2 с (требование S2) |

### 3.3 Корреляция: `psim.events.normalized.v1` -> `psim.signals.v1`

| Свойство | Значение |
|---|---|
| Производитель | Correlation Engine |
| Потребители | Incident Service (`psim-incident`), Projection Service |
| Ключ | `grouping_key` сигнала |
| Порядок | В пределах ключа группировки |
| Семантика | EOS-K: выходные сигналы, записи changelog и смещения входа - в одной транзакции |
| Идемпотентность | Детерминированный `signal_id` (SG1); защита на стороне Incident Service - inbox |
| Retention | 7 суток |

Ключ выходного топика - `grouping_key`, а не `correlation_key` из плана: Incident Service получает все сигналы одного будущего инцидента в одной партиции и в порядке. Это исключает гонку двух экземпляров при создании инцидента по одному ключу. Фиксируется в ADR-007.

**Внутренние топики корреляции:**

| Топик | Ключ | Назначение |
|---|---|---|
| `psim.correlation.changelog.v1` | `state_key` = `rule_id + correlation_key` | Compacted; восстановление RocksDB. Партиции совпадают с входным топиком один к одному |
| `psim.correlation.repartition.v1` | `correlation_key` | Отфильтрованные события для правил, чей ключ не выводится из зоны (например, площадка). Запись в той же транзакции; читается тем же сервисом |

**Время.** Правила работают по event time. Водяной знак партиции - минимум по источникам партиции из `max(occurred_at) - allowed_lateness`, с исключением неактивных источников по таймауту простоя. Правила `conjunction`, `sequence` и `single` срабатывают в момент прихода завершающего события, не дожидаясь водяного знака. Правила `threshold` и `absence` закрывают окно по водяному знаку. События позже допустимого опоздания не учитываются в закрытых окнах и подсчитываются в метрике. Подробности - ADR-010.

**Поведение при сбоях:**

| Сбой | Поведение |
|---|---|
| Падение экземпляра | Транзакция прерывается; новый владелец восстанавливает RocksDB из changelog (≤ 30 с), продолжает с зафиксированного смещения |
| Ребалансировка | Кооперативная: отзываются только переназначаемые партиции; перед отзывом транзакция фиксируется |
| Смена набора правил | Применяется на границе смещения `psim.config.v1` (RS2); состояние неизменённых правил сохраняется (RS3) |
| Ошибка вычисления правила для события | Событие и ошибка - в `psim.dlq.correlation.v1`; остальные правила обрабатывают событие |

### 3.4 Инциденты: `psim.signals.v1` -> PostgreSQL -> `psim.incidents.events.v1`

| Свойство | Значение |
|---|---|
| Производитель | Incident Service (outbox) |
| Потребители | Response Engine (`psim-response`), Projection Service, API Gateway realtime (чтение без группы, все партиции), Audit Service (через `psim.audit.v1`) |
| Ключ | `incident_id` |
| Порядок | В пределах инцидента; события несут `version` агрегата без пропусков |
| Семантика | Вход EOS-DB (inbox по `signal_id`), выход Outbox |
| Идемпотентность | Потребители применяют событие, только если `version` больше применённой; повтор с той же версией игнорируется |
| Retention | 30 суток (источник для перестроения проекций и отчётов) |

Порядок публикации outbox: реле публикует записи в порядке `outbox_id` в пределах агрегата; при нескольких экземплярах реле партиции outbox распределяются по `hash(incident_id)`, чтобы один агрегат публиковал только один экземпляр.

**Поведение при сбоях:**

| Сбой | Поведение |
|---|---|
| Падение после коммита БД, до фиксации смещения | Сигнал приходит повторно; inbox отбрасывает его |
| Падение реле после публикации, до пометки | Событие публикуется повторно с той же версией; потребители его игнорируют |
| Недоступна PostgreSQL | Потребление сигналов приостанавливается (противодавление); сигналы копятся в Kafka; после восстановления - догоняющая обработка |
| Переключение PostgreSQL на реплику | Синхронная репликация: зафиксированные транзакции не теряются (RPO = 0) |

### 3.5 Реагирование: `psim.response.events.v1`

| Свойство | Значение |
|---|---|
| Производители | Response Engine, Command Service, Notification Service (outbox) |
| Потребители | Incident Service (`blocking_steps`, хронология), Projection Service, API Gateway realtime, Notification Service |
| Ключ | `incident_id`; для команд и уведомлений вне инцидента - `command_id` или `notification_id` |
| Порядок | В пределах инцидента |
| Семантика | Outbox; потребители - EOS-DB или по версии агрегата |
| Retention | 30 суток |

В топике публикуются события запусков сценариев, жизненного цикла команд и уведомлений. Отдельные топики для жизненного цикла команд не вводятся: консоли и проекциям нужен единый поток по инциденту.

### 3.6 Команды: `psim.commands.v1` и `psim.commands.results.v1`

| Свойство | `psim.commands.v1` | `psim.commands.results.v1` |
|---|---|---|
| Производитель | Command Service (outbox) | Connector Gateway |
| Потребители | Все экземпляры Connector Gateway: каждый читает все партиции и доставляет команду, если сессия коннектора у него | Command Service (`psim-command`) |
| Ключ | `connector_id` | `command_id` |
| Порядок | В пределах коннектора | В пределах команды |
| Семантика | ALO+ID: SDK исполняет `command_id` не более одного раза и возвращает сохранённый результат | ALO+ID: результат для финальной команды игнорируется (CM5) |
| Retention | 24 ч | 24 ч |

Широковещательное чтение выбрано потому, что объём команд мал (единицы в секунду), а маршрутизация через реестр сессий добавляет зависимость от Redis на критичном пути. Перед отправкой Command Service проверяет реестр сессий: если коннектор не в сети, команда сразу завершается с `failed: CONNECTOR_OFFLINE`. Если сессия пропала между проверкой и доставкой, ни один экземпляр не доставит команду, и она завершится по `deadline_at` со статусом `timed_out`. Реестр сессий здесь используется только для быстрого отказа, а не для доставки. Решение фиксируется в ADR-018.

### 3.7 Каталог: `psim.catalog.v1`

| Свойство | Значение |
|---|---|
| Производитель | Resource Catalog (outbox) |
| Потребители | Normalizer, Connector Gateway, Correlation Engine, Response Engine, Command Service, Projection Service, API Gateway (ABAC: принадлежность зон площадкам) |
| Ключ | `resource_type + ":" + resource_id` |
| Семантика | Compacted; запись - полное актуальное состояние ресурса с версией |
| Чтение | Каждый экземпляр читает топик целиком без группы потребителей, строит копию в памяти и считается готовым (readiness) после чтения до конца |
| Retention | Бессрочно (compaction) |

### 3.8 Конфигурация: `psim.config.v1`

| Свойство | Значение |
|---|---|
| Производители | Correlation Engine (наборы правил), Normalizer API (правила отображения), администрирование системы |
| Ключ | `config_key`: `ruleset/<tenant>`, `mapping/<tenant>/<connector_type>`, `retention/<tenant>`, `system/<name>` |
| Партиции | 1 - единый порядок применения всех изменений конфигурации |
| Семантика | Compacted; запись - полный активный объект с версией |
| Применение | Потребитель применяет изменение атомарно между пакетами входных данных |

### 3.9 Аудит: `psim.audit.v1`

| Свойство | Значение |
|---|---|
| Производители | Все сервисы (outbox или в транзакции Kafka для Normalizer и Correlation Engine) |
| Потребители | Audit Service (`psim-audit`) |
| Ключ | `tenant_id` |
| Порядок | В пределах тенанта - порядок записи в цепочку |
| Семантика | ALO + идемпотентность по `source_event_id` (AU3) |
| Retention | 30 суток (источник истины после записи - PostgreSQL Audit Service) |

### 3.10 Ошибки: `psim.dlq.<stage>.v1`

| Свойство | Значение |
|---|---|
| Производители | Этапы конвейера: `normalizer`, `correlation`, `incident`, `response`, `command`, `audit`, `projection` |
| Ключ | Исходный ключ сообщения |
| Содержимое | Исходные байты без изменений; заголовки: `psim-dlq-stage`, `psim-dlq-error-code`, `psim-dlq-error`, `psim-dlq-source-topic`, `psim-dlq-source-partition`, `psim-dlq-source-offset`, `psim-dlq-at` |
| Обработка | CLI администратора: просмотр, повторная обработка в исходный топик, отбрасывание с записью аудита |
| Retention | 14 суток |

Правило: в DLQ попадают только сообщения, которые не обработать без вмешательства (невалидные данные, отсутствующие справочники). Временные ошибки (недоступность хранилища) приводят к паузе и повторам, а не к DLQ - иначе нарушится порядок.
