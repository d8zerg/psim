# ADR-012. Исполнение сценариев реагирования и сервис таймеров

- **Статус:** Предложено (принимается в начале шага 6.1)
- **Дата:** 2026-10-06
- **Шаг плана:** 6.1
- **Связанные:** ADR-008, [aggregates.md](../domain/aggregates.md#5-response), [state-models.md](../domain/state-models.md#2-запуск-сценария)

## Контекст

Сценарии реагирования - графы шагов с ветвлениями, ожиданиями, командами и эскалациями. Исполнение должно переживать перезапуск сервиса с той же точки, фиксировать версию сценария при запуске, а таймеры (SLA, ожидания, дедлайны команд) - срабатывать с погрешностью ≤ 1 с ровно один раз.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Внешний движок рабочих процессов (Temporal, Camunda/Zeebe) | Готовая надёжность исполнения | Отдельная тяжёлая подсистема (Go/Java, своя БД или Elasticsearch) в поставке; лицензионные изменения у Camunda; модель BPMN избыточна для чек-листов |
| Таймеры в Kafka (отложенные сообщения через топики с задержкой) | Без БД | Kafka не поддерживает отложенную доставку; эмуляция сложна и неточна |
| Таймеры в Redis (sorted set) | Быстро | Redis не источник истины (ADR-015) |
| **Собственный интерпретатор графа сценария; состояние запуска и таймеры в PostgreSQL сервиса; опрос таймеров владельцем партиции** | Простая модель под наш домен; атомарность с outbox; без новых подсистем | Своя реализация; опрос нагружает БД (небольшой объём таймеров) |

## Предлагаемое решение

1. `ResponseRun` - агрегат в PostgreSQL Response Engine; переходы шагов - доменная логика ([state-models.md](../domain/state-models.md#22-шаг)); каждое изменение - транзакция с outbox.
2. Библиотека `libs/platform/timers`: таблица `timers(timer_id, partition, due_at, kind, payload, fired_at)` в схеме сервиса-владельца. Таймер привязан к партиции ключа (инцидента или команды); экземпляр, владеющий партицией входного топика, опрашивает свои таймеры каждые 200 мс (`due_at ≤ now`, `FOR UPDATE SKIP LOCKED`).
3. Срабатывание таймера - транзакция: пометка `fired_at` + доменное действие + outbox; идемпотентность по `timer_id` (повтор после падения не дублирует действие).
4. Таймеры используют Response Engine (SLA, ожидания, эскалации) и Command Service (дедлайны команд).

## Последствия

- Погрешность срабатывания = интервал опроса + время транзакции (≤ 1 с с запасом).
- При ребалансировке таймеры переходят вместе с партицией без отдельной координации.

## Проверка

Тест: перезапуск сервиса посреди сценария и перед срабатыванием таймера; замер погрешности таймеров под нагрузкой.
