# ADR-054. История событий, связи и продление хранения

- Статус: Принято
- Шаг: 5.4
- Связанные решения: ADR-020, ADR-028, ADR-045, ADR-052, ADR-053

## Контекст

Существующий загрузчик сохраняет нормализованные события с индивидуальным TTL. Для разбора инцидента нужны исходные события сигналов, статистика версий правил и продление хранения событий, значимость которых стала известна после нормализации. Сигнал и событие могут поступить в историю в разном порядке. Данные инцидентов принадлежат Incident Service; Event History хранит восстанавливаемую проекцию связей.

## Решение

1. Сохранить прежнюю миграцию `events` и журнал её загрузчика. Отдельный загрузчик того же процесса читает `psim.signals.v1` и `psim.incidents.events.v1`, фиксирует подготовленные native-блоки в PostgreSQL и записывает `history_facts`. Строка соответствует входному сообщению; логическая дедупликация выполняется `ReplicatedReplacingMergeTree` и `FINAL`. Нормализованные события и факты имеют независимые группы Kafka и идентификаторы транзакционных продюсеров.
2. `signal_facts`, `event_signals` и `incident_signals` - обычные представления над дедуплицированными фактами. Связи разворачиваются из массива уникальных event_id. Так нет отдельной вставки, после сбоя которой факты и связи могли бы разойтись. Для инцидента используются явные signal_id событий создания и присоединения, включая сигналы за пределами preview из 1000 элементов.
3. Дополнительный потребитель сигналов идемпотентно сохраняет запросы продления в PostgreSQL. Пакет обработки блокирует строки через `SKIP LOCKED`, ищет тела событий в ClickHouse и вставляет значимые копии в `retained_events`. Только после подтверждения вставки удаляется запрос. Сбой может повторить физическую запись, но `ReplacingMergeTree` с версией срока хранения и `FINAL` сохраняет один логический результат с максимальным сроком. Повтор и более короткая политика не сокращают уже продлённое хранение.
4. Сигнал раньше события оставляет ожидающий запрос. Отсутствующие тела повторно проверяются до конца срока значимого хранения; после этого запрос удаляется. Уже удалённое тело не восстанавливается из одной ссылки. API возвращает недоступные event_id отдельно. Исходный нормализованный топик не изменяется; признак значимости уточняется в копии истории.
5. Типовой срок для всех событий - 7 суток, для значимых событий и связей - 90 суток. `RetentionSettings` применяется к новым подготовленным блокам и новым запросам продления. Конфигурация восстанавливается перед началом обработки. Все таблицы с данными имеют TTL; запросы также исключают истёкшие строки до физического удаления фоновым слиянием.
6. HTTPS API проверяет JWT и общую библиотеку авторизации. Поиск, статистика, связи и тела всегда ограничены тенантом и временем, а также площадками и зонами пользователя до пагинации. Администратор не получает права оператора автоматически. Отказы роли пишутся в долговечный outbox аудита. Внешняя маршрутизация остаётся в шаге 7.1.
7. Параметризованное чтение ClickHouse принимает только постоянный проверенный SELECT. Значения тенанта и интервала зарезервированы; фильтры передаются native-параметрами. Результат ограничен по строкам, байтам и времени. Курсор связан с запросом, субъектом и областью доступа; он не даёт дополнительных прав.

## Альтернативы

- Отдельная вставка каждой связи или materialized view с собственной таблицей усложняет восстановление после частичного успеха и повторной вставки. Представление над фактом сохраняет соответствие без дополнительной распределённой транзакции.
- Частые мутации TTL исходных строк ClickHouse создают дополнительную работу слияния и требуют согласования с повторной загрузкой. Отдельные копии значимых событий имеют монотонную версию срока хранения.
- Синхронный запрос события во время обработки сигнала не поддерживает обратный порядок доставки. Долговечная очередь сохраняет ожидание и переживает перезапуск.

## Проверка

`task history:test`, `task history:sanitizers`, `task history:coverage`, `task history:bench`. Проверки используют две настоящие службы, Kafka, PostgreSQL, ClickHouse с Keeper и Keycloak. Поиск за сутки измеряется во время записи не менее 50 000 событий/с. Короткий локальный прогон не заменяет длительные проверки кластерной поставки.
