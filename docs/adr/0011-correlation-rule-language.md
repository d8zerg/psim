# ADR-011. Язык правил корреляции

- **Статус:** Предложено (принимается в начале шага 5.1)
- **Дата:** 2026-10-06
- **Шаг плана:** 5.1
- **Связанные:** ADR-009, ADR-010, [aggregates.md](../domain/aggregates.md#33-агрегат-correlationrule)

## Контекст

Администратор описывает правила корреляции без программирования; правила должны валидироваться до активации, исполняться детерминированно и быстро (50 000 событий/с на трёх экземплярах), прогоняться на истории и не давать администратору выполнить произвольный код в ядре. Риск плана: «разрастание языка правил».

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Встроенный скриптовый язык (Lua, JavaScript) | Максимальная гибкость | Тьюринг-полнота: бесконечные циклы, неограниченная память, трудно валидировать и анализировать; угроза безопасности; правила неразбираемы для редактора и пробного прогона |
| SQL-подобный язык событий (как Esper EPL, Flink SQL) | Выразительность | Сложный собственный парсер и планировщик; высокий порог для администраторов |
| Полностью декларативная модель без выражений | Простота валидации | Условия на атрибуты и вычисление приоритета требуют бесконечного расширения модели |
| **Декларативная модель видов правил + выражения CEL для условий и вычислений** | Структура правила (вид, окно, ключ, шаги последовательности) - декларативна и анализируема; условия и приоритет - на CEL: не Тьюринг-полный, с оценкой стоимости, типизируется при компиляции; есть реализация на C++ (cel-cpp, Apache 2.0) на том же стеке Protobuf | Зависимость от cel-cpp (abseil, protobuf); ограничения CEL нужно документировать для администраторов |

## Предлагаемое решение

1. Правило - документ (YAML в редакторе, Protobuf в хранилище и в `psim.config.v1`) с фиксированными видами: `single`, `conjunction`, `sequence`, `threshold`, `absence` ([aggregates.md](../domain/aggregates.md#33-агрегат-correlationrule)).
2. Поля, где нужны выражения (`condition`, `priority`, `summary`), - выражения CEL над типизированным событием (`event.type`, `event.severity`, `event.attributes[...]`, `event.zone_id`) и переменными правила. Выражения компилируются и проверяются по типам при валидации; стоимость ограничивается лимитом.
3. Фильтр по типу таксономии вынесен в отдельное декларативное поле, чтобы движок индексировал правила по типам событий и вычислял CEL только для подходящих событий.
4. Новые виды правил добавляются только через ADR (мера против разрастания).

## Последствия

- Скомпилированные программы CEL кэшируются на версию набора правил.
- Нагрузочный тест шага 5.2 должен подтвердить стоимость вычисления CEL на горячем пути; запасной вариант - собственный интерпретатор подмножества выражений с тем же синтаксисом.

## Проверка

Фаззинг парсера и валидатора правил 24 ч (DoD шага 5.1); бенчмарк вычисления правил.
