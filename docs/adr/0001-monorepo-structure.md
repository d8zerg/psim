# ADR-001. Структура монорепозитория и границы модулей

- **Статус:** Принято
- **Дата:** 2026-10-06
- **Шаг плана:** 0.4 (реализация - 1.1, 1.2)
- **Связанные:** [context-map.md](../domain/context-map.md), [crosscutting.md](../architecture/crosscutting.md#12-тестируемость-и-структура-модулей)

## Контекст

Платформа состоит из ~12 сервисов на C++, библиотек платформы, контрактов, веб-приложения, коннекторов, артефактов развёртывания и документации. Разработку ведут один инженер и ИИ-агент: важны атомарные изменения контракта вместе с кодом, единая сборка и автоматическая проверка границ модулей.

## Рассмотренные варианты

### Вариант A. Полирепозиторий (репозиторий на сервис)

- Независимые версии и выпуски.
- Изменение контракта требует согласованных изменений в нескольких репозиториях; дублирование инфраструктуры сборки; для одного инженера - чистые накладные расходы.

### Вариант B. Модульный монолит (один процесс)

- Проще развёртывание и отладка.
- Противоречит требованиям горизонтального масштабирования по этапам конвейера и обновления без простоя по сервисам.

### Вариант C. Монорепозиторий с независимыми сервисами, раскладка по слоям (`domain/`, `adapters/` на верхнем уровне)

- Единая сборка.
- Код одного контекста разнесён по дереву; границы контекстов не видны.

### Вариант D. Монорепозиторий с независимыми сервисами, раскладка по контекстам

- Единая сборка и атомарные изменения; границы контекстов совпадают с деревом каталогов и целями CMake; проверка зависимостей автоматизируется.
- Требует дисциплины в направлениях зависимостей (решается fitness function).

## Решение

Вариант D. Структура:

```
contracts/                  публичные контракты (единственный источник истины)
  proto/psim/...            Protobuf: конверт, события топиков, протокол коннекторов, REST DTO
  asyncapi/                 описание топиков
  taxonomy/                 таксономия событий (машиночитаемая)
  errors/                   каталог кодов ошибок
libs/
  platform/                 общие библиотеки: runtime, async, kafka, pg, redis, security,
                            observability, config, outbox, timers, ids, clock
  sim/                      детерминированный симуляционный стенд
  domain/<context>/         доменные ядра: catalog, ingest, processing, incident, response,
                            access, audit (чистые библиотеки)
services/<service>/         application + adapters + main; один исполняемый файл на сервис
connectors/
  sdk/                      Connector SDK (C++)
  conformance/              тестовый набор соответствия
  simulator/                симулятор и генератор нагрузки
  <reference>/              эталонный коннектор (Q2)
web/                        pnpm + Turborepo: apps/console, packages/*
tools/psimctl/              CLI администратора
deploy/                     compose, systemd, deb, installer, observability
tests/                      e2e, load, chaos, contract
docs/                       документация, ADR, архитектура
```

Правила зависимостей:

1. `libs/domain/*` зависят только от стандартной библиотеки и `libs/domain/common` (общие типы значений). Никаких Boost.Asio, librdkafka, libpq, сетевых и системных часов.
2. `services/*` зависят от своего доменного ядра, `libs/platform` и сгенерированного кода контрактов. Сервис не зависит от другого сервиса.
3. Доменные ядра разных контекстов не зависят друг от друга; общение - через контракты.
4. Управление правилами корреляции - модуль сервиса Correlation Engine, отдельного сервиса нет.
5. Сервис таймеров - библиотека `libs/platform/timers`, отдельного сервиса нет.

## Последствия

- Изменение контракта, кода и документации - один коммит; CI проверяет всё вместе.
- Число сервисов в MVP: Connector Gateway, Resource Catalog, Normalizer, Event History, Correlation Engine, Incident Service, Response Engine, Command Service, Notification Service, Projection Service, Audit Service, API Gateway.
- Сборка всего дерева растёт; смягчается кэшем компиляции и сборкой только затронутых целей в CI.
