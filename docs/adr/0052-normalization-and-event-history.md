# ADR-052. Normalization, Source Cursors, and Event History

<!-- language-links -->
[English](0052-normalization-and-event-history.md) | [Русский](../ru/adr/0052-normalization-and-event-history.md)
<!-- /language-links -->

- Status: Accepted
- Related decisions: ADR-006, ADR-010, ADR-028, ADR-042, ADR-045, ADR-051

## Context

The Normalizer should replace the fixed catalog of the test environment with its own copies of resources, apply declarative mappings, and eliminate duplicate deliveries until correlation occurs. Rebooting, rolling back transactions, and changing the owner of a partition should not lead to repeated publication or missing events. Event History retains normalized events regardless of the freshness of the device’s state.

## Solution

1. The Normalizer uses the common group `psim-normalizer`. Each instance restores its own copies of `psim.catalog.v1` and `psim.config.v1` from the beginning up to the specified upper offsets. A manual consumer using `read_committed` takes into account EOF messages, transaction markers, and compaction gaps. An unacknowledged transaction blocks restoration; a limited timeout prevents processing from starting with an incomplete state. Resource archiving is sent in its full version, not as a tombstone.
2. The catalog copy compares resource versions within a shard. The source is verified against the device and connector; the device, type, zone, and connector must be active. Unknown sources, disabled resources, and no mapping result in a constant error with an original message in the DLQ. New management versions are applied between input packets.
3. Mappings are selected by tenant and connector type. The first match of exact code or prefix with the final `*` determines the taxonomy type and severity. A limited subset of CEL is supported: strings, boolean, `!`, `&&`, `||`, brackets, `==`, `!=`, `has`, `startsWith`, `endsWith`, `contains`; available are `raw.raw_code`, `raw.source_ref`, `raw.attributes["name"]`. Missing attributes do not satisfy comparison. Unsupported constructs are rejected during configuration loading. Expression limits are 4000 characters and depth 32. Scripting, regular expressions, and arbitrary functions are not allowed.
4. Taxonomy is read from the provided YAML file. Original code, event identifier, sequence, epoch, and times are preserved. Unmapped attributes get a prefix `x.`. The default significance threshold is medium; overrides come from `ProcessingSettings`.
5. The cursor has the key `<tenant_id>/<source_id>:<epoch>` and a bit map of the last 4096 numbers. Different epochs retain independent maps. Duplicates within the map are discarded; previously unseen numbers within the window are accepted. Numbers outside the window are sent to DLQ: it is no longer possible to distinguish duplicates from previously unseen events. There is no hidden deletion of cursors by time; the size of copies is limited by configuration. Changing the number of input partitions requires a separate state transfer procedure.
6. Normalized events, new cursors, and input offsets are fixed in one Kafka transaction. Before commit, cursors are in a separate set. Only the last snapshot of each source is sent to the log per transaction; all intermediate accepted numbers remain in the bit map. A normal commit first sends these snapshots. The target commit interval is 5 ms; at least 5 ms is maintained between transaction completion and the start of the next one so that the coordinator can complete markers before the new AddPartitionsToTxn. The delay of commit is displayed separately as a histogram. Revoking partitions aborts an unfinished transaction, as asynchronous preparation of snapshots is not available within a synchronous callback. Abort discards the staged cursors and seeks back to replay the input. When a partition is assigned, cursors are restored from the corresponding compacted log. The state of the revoked partition is removed. `transactional.id` distinguishes instances; the generation of groups prevents commits by the previous owner through KIP-447.
7. `live_observation` and `state_observed_at` only appear for recent observations with matching identifiers in the observing and receiving sessions. Older observations do not increase the saved time of acknowledgment even when epochs are changed or rebooted. Other events are retained in history. The projection must additionally verify the session with the current state of the Gateway and compare times; the connection itself does not confirm the device’s state.
8. Event History uses the common group `psim-event-history` and a platform loader with a durable log of prepared blocks in PostgreSQL. Batch boundaries, bytes and the insert token are preserved until ClickHouse delivery completes. The size of a prepared block is limited to 8 MiB; if data exceeds this limit after conversion, the loader reduces the packet to an acceptable prefix. The remainder is read after the prefix commits. After insertion, DLQ and input offsets are fixed. Retries use the original block and token; `ReplicatedReplacingMergeTree` ensures logical uniqueness when reading from `FINAL` after the deduplication window of insertions ends.
9. The table `events` has daily partitions and the key `(tenant_id, site_id, zone_id, occurred_at, event_id)`, indexes by device, type, and event identifier. Type and original code use LowCardinality. Full Protobuf is preserved for future query development. `expires_at` is calculated from the event time and current tenant settings: by default 7 days for all events and 90 for significant ones. New policies apply to new prepared blocks; changing the duration of already saved rows requires separate recalculation. Prepared blocks do not change during restoration.

## Verification

`task processing:test` verifies three instances of Normalizer and two history loaders, duplicate input, verification of Kafka and ClickHouse identifiers, SIGKILL, partition transfer, and continued processing after DLQ. `task processing:sanitizers` performs ASan/UBSan and TSan checks. `task processing:coverage` measures module and integration paths. Load criteria are checked separately from functional verification; results of a small separate run do not confirm cluster performance.
