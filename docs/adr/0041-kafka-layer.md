# ADR-041. Слой Kafka

- **Статус:** Принято
- **Дата:** 2026-10-07
- **Шаг плана:** 2.3
- **Связанные:** ADR-002 (Kafka и librdkafka), ADR-003 (Schema Registry), ADR-004 (wire format), ADR-005 (заголовки трассировки), ADR-006 (семантика доставки; уточняет механизм EOS-K), ADR-016 и [ADR-040](0040-async-primitives.md) (модель исполнения), [crosscutting.md](../architecture/crosscutting.md#33-транзакции-kafka-eos-k) раздел 3.3 и раздел 4, методы TS-03, B-01, FF-04

## Контекст

Шаг 2.3: библиотека Kafka-клиента. Нужны: интеграция librdkafka с Asio без блокирующих опросов, идемпотентный продюсер и транзакции, потребитель с ручной фиксацией смещений и корректной ребалансировкой, пакеты, противодавление, повторы и DLQ, Protobuf в формате Schema Registry с кэшем схем, контекст трассировки в заголовках, метрики лагов и пропускной способности. DoD: интеграционные тесты подтверждают отсутствие потерь и exactly-once при принудительных падениях; ≥ 200 000 сообщений/с на продюсер и потребитель.

ADR-006 и crosscutting.md 3.3 предписывали для EOS-K один транзакционный продюсер на назначенную партицию входа (`transactional.id = <service>-<topic>-<partition>`). Это схема до KIP-447: при 12-48 партициях на экземпляр - десятки клиентов librdkafka со своими потоками и соединениями.

## Рассмотренные варианты

### Интеграция librdkafka с Asio

| Вариант | Плюсы | Минусы |
|---|---|---|
| Поток опроса на клиент (`rd_kafka_poll` в цикле) | Просто | Лишние потоки и переключения; обратные вызовы в чужом потоке требуют синхронизации с шардом |
| Фоновая очередь librdkafka (`rd_kafka_queue_get_background`) | Без опроса | Обратные вызовы в потоке librdkafka - та же синхронизация |
| **`rd_kafka_queue_io_event_enable` + eventfd в Asio** | Обратные вызовы в шарде владельца; без потоков и блокировок (ADR-016, п. 5) | Сигнал только при переходе «пусто - не пусто»: очередь вычерпывается до ожидания, страховочное пробуждение раз в 100 мс |

### Exactly-once (EOS-K)

| Вариант | Плюсы | Минусы |
|---|---|---|
| Продюсер на партицию входа (ADR-006 в исходной редакции) | Изоляция партиций | Десятки клиентов на экземпляр; создание продюсеров при каждой ребалансировке |
| **Продюсер на потребителя (KIP-447): `send_offsets_to_transaction` с метаданными группы** | Один транзакционный продюсер на шард; «зомби» отсекаются поколением группы, повторный запуск - `transactional.id` | Транзакция охватывает все партиции шарда: откат возвращает их все |

### Ребалансировка

Протокол группы - **KIP-848** (`group.protocol=consumer`, Kafka 4.x), классический кооперативный - настройкой. Статическое членство (`group.instance.id`) отклонено: в протоколе KIP-848 перезапуск упавшего члена с тем же id до истечения его сессии брокер отвергает (`UNRELEASED_INSTANCE_ID`), librdkafka считает это фатальной ошибкой. Партиции упавшего члена переходят к другим по истечении `group.consumer.session.timeout.ms` (по умолчанию 45 с; в локальном окружении 10 с).

## Решение

Библиотека `libs/platform/kafka` (`psim::platform_kafka`), слой infrastructure; клиенты привязаны к исполнителю шарда, как примитивы ADR-040.

1. **Producer** - всегда идемпотентный: `enable.idempotence=true`, `acks=all` фиксированы, переопределение - ошибка конфигурации; по умолчанию zstd, `linger.ms=5`. `enqueue` ждёт только при заполненной локальной очереди (противодавление через `WaitList`), итог доставки сообщает `flush`; `send` ждёт подтверждения (`acks=all` перед ответом коннектору, ADR-006 п. 2). Отчёты о доставке обслуживает корутина по событию очереди.
2. **Транзакции:** `transactional_id = <service>-<instance>-<shard>`; `init/commit/abort` - блокирующие вызовы librdkafka - в `BlockingPool` (ADR-016 п. 4), перед фиксацией сообщения доставляются асинхронно, так что сама фиксация не ждёт отправки. После неудачной фиксации транзакция откатывается; `fatal()` (отсечение более новым экземпляром, фатальная ошибка идемпотентности) - продюсер пересоздаётся, этап завершается с ошибкой.
3. **Consumer** - смещения только вручную (`enable.auto.commit=false`, `enable.auto.offset.store=false`), `read_committed` для входов EOS-K; `poll` возвращает пакет и отбрасывает сообщения партиций, отозванных во время него. Ребалансировка доходит до `RebalanceListener` внутри `poll`, то есть между пакетами; при отзыве сделанное фиксируется синхронно. `close` выходит из группы асинхронно (не дольше 30 с), без него член группы уходит по таймауту сессии.
4. **Processor** - цикл «прочитать - обработать - записать» шарда; логика этапа - реализация интерфейса `Handler::handle(const Message*, Output*)` (указатели вместо ссылок в параметрах корутин, ADR-040):
   - ALO: выходы доставляются (`flush`), затем фиксируются смещения (раз в `commit_interval`, по умолчанию 1 с); при ошибке доставки партиции возвращаются к зафиксированным смещениям;
   - EOS-K: выходы, DLQ и смещения - в одной транзакции (интервал 20-50 мс, ADR-006 п. 5); при сбое - откат и возврат партиций к началу транзакции;
   - ошибки обработчика: повторяемая (`retryable` по каталогу) - перемотка партиции на сообщение, пауза и возобновление с экспоненциальной задержкой, остальные партиции продолжают (ADR-006 п. 4); неповторяемая - DLQ `psim.dlq.<stage>.v1` с исходными байтами и заголовками `psim-dlq-*` (data-flows.md 3.10); исключение - ошибка программы: DLQ и останов партиции после `circuit_breaker` подряд (crosscutting.md 4).
5. **Сериализация:** `ProtobufSerde<T>` - Confluent wire format (магический байт, id схемы, индексы сообщения zigzag-varint, тело). Id схемы писателя - последняя версия субъекта `<topic>-value`, определяется при старте (`SchemaRegistry` - тонкий клиент на Beast с кэшем по id); чтение принимает любой id - совместимость версий обеспечивает FF-04, реестр не на горячем пути (ADR-003). Неверный формат или чужой тип - `PROCESSING_PAYLOAD_INVALID` (DLQ).
6. **Регистрация схем** - `tools/contracts/registry.py` (установщик и CI, ADR-003): значение каждого топика из `contracts/topics/topics.yaml` с импортами как ссылками; импортируемые файлы - отдельные субъекты по пути импорта с `FULL_TRANSITIVE`, субъекты топиков - `BACKWARD_TRANSITIVE` (ADR-004); `google/protobuf/*` встроены в реестр. `task contracts:registry:register`.
7. **Трассировка:** `inject`/`extract` W3C `traceparent`/`tracestate` в заголовках (разбор и форматирование `traceparent` - свои: пропагатор OpenTelemetry даёт ложное срабатывание анализатора `security.ArrayBound`, выключать проверку безопасности ради него не стоит), `start_consumer_span` - спан CONSUMER с родителем из сообщения.
8. **Метрики** (`KafkaMetrics`, одна на процесс): `psim_kafka_produced_messages_total`, `psim_kafka_produced_bytes_total`, `psim_kafka_delivery_errors_total`, `psim_kafka_consumed_messages_total`, `psim_kafka_consumed_bytes_total` (по топику), `psim_kafka_consumer_lag{group,topic,partition}` (статистика librdkafka раз в 5 с), `psim_kafka_rebalances_total`, `psim_kafka_retries_total`, `psim_kafka_dead_letters_total{stage,code}`, `psim_kafka_transactions_total{result}`, `psim_kafka_stopped_partitions`.
9. **Сборка librdkafka** (профили Conan, `tools/conan/profiles`):
   - `rd_atomic32_set`/`rd_atomic64_set` в librdkafka 2.14 проверяют макросы `HAVE_ATOMICS_{32,64}_ATOMIC`, которые её сборка не определяет, и становятся обычной записью - гонка данных, найденная TSan; макросы задаются флагами компиляции во всех профилях, флаги входят в package id;
   - ThreadSanitizer не перехватывает потоки C11 glibc (`thrd_create`, `mtx_*`, `cnd_*`): в профиле TSan определение C11 потоков librdkafka отключено переименованием `thrd_create`, и она использует свою реализацию поверх pthreads;
   - в профиль clang-tidy (ADR-033) - выключен `readability-redundant-member-init`: `{}` у поля структуры параметров отмечает необязательное поле для назначенной инициализации, иначе `-Wmissing-designated-field-initializers` требует перечислять все поля.
10. **Проверка в конвейере:**
   - TS-03 - `task test:component`: компонентные тесты (метка CTest `component`, исключены из пресетов) в контейнере toolchain в сети окружения; покрытие модулей с `measured_by: component` в `tools/cpp/coverage.yaml` проверяется по профилям модульных и компонентных тестов вместе;
   - FF-04 - `task contracts:registry-compat`: схемы последнего выпуска (до первого - `master`), затем рабочего дерева, под временным префиксом субъектов;
   - B-01 - `task bench:kafka` (ночной);
   - все три - в `env:ci-test`; этап `env` включается и изменениями слоя Kafka и контрактов.

## Последствия

- Уточнение ADR-006 и crosscutting.md 3.3: один транзакционный продюсер на шард, а не на партицию; гарантия exactly-once та же.
- Время восстановления после падения экземпляра - таймаут сессии группы; для этапов с жёстким бюджетом задержки его настраивает установщик (шаг 9.1).
- Обработка внутри шарда последовательна; параллелизм - число шардов и партиций (ADR-016).
- Сервисы шагов 3-6 получают `Processor` и пишут только обработчик.

## Проверка

- Модульные тесты: wire format, serde, задержки повторов, ошибки конфигурации и доставки без брокера, клиент реестра против поддельного HTTP-сервера.
- Компонентные тесты (TS-03):
  - доставка ключей, значений, заголовков и контекста трассировки;
  - разрыв соединения с брокером через Toxiproxy без потерь и дубликатов;
  - `read_committed` не видит отменённых транзакций;
  - повторы, DLQ, предохранитель;
  - ребалансировка без потерь;
  - serde со схемой из реестра;
  - процесс обработки убивается SIGKILL в случайные моменты: EOS-K - каждое сообщение ровно один раз, ALO - без потерь.
- B-01 - пропускная способность на Docker Desktop.
