# ADR-034. Локальный конвейер CI/CD и цепочка поставки

- **Статус:** Принято
- **Дата:** 2026-10-06
- **Шаг плана:** 1.3
- **Связанные:** ADR-030, ADR-031, ADR-032, ADR-033, требования SR-23 и SR-24 ([threat-register.md](../security/threat-register.md)), [strategy.md](../quality/strategy.md#4-барьеры)

## Контекст

Шаг 1.3 требует конвейер от коммита до подписанного артефакта: сборка, статический анализ, тесты, санитайзеры, контракты, интеграционные тесты, бенчмарки, пакеты и образы, SBOM CycloneDX, проверка лицензий и уязвимостей, подпись. DoD: каждое изменение проходит полный конвейер, релизный артефакт содержит SBOM и подпись.

Решение владельца продукта (2026-10-06): конвейер выполняется локально на стенде разработчика (Docker Desktop); git-хостинг - только хранилище кода, конвейеров на хостинге нет. Разработку ведут один инженер и ИИ-агент, коммиты и push делает инженер.

Требования безопасности: SR-23 - зависимости закреплены lock-файлами, базовые образы и образы инструментов - по дайджесту, SBOM, блокирующая проверка лицензий и уязвимостей, воспроизводимые сборки; SR-24 - подпись артефактов, проверка подписи установщиком, контейнеры без root, с файловой системой только для чтения и без лишних capabilities.

## Рассмотренные варианты

### Где выполняется конвейер

| Вариант | Плюсы | Минусы |
|---|---|---|
| CI хостинга (GitHub Actions) | Барьер на стороне сервера | Противоречит решению владельца; раннеры без Docker Desktop стенда; секреты подписи на хостинге |
| Собственный CI-сервер (Jenkins, Woodpecker) на стенде | Барьер на сервере | Ещё одна система для одного инженера; дублирует то, что уже делают задачи Task |
| **Задачи Task на стенде + хук `pre-push`** | Тот же набор задач, что разработчик запускает руками (ADR-030); проверяется ровно та среда, где проверяется DoD; нет внешних систем | Барьер на стороне клиента: `--no-verify` обходит его - смягчается записью о прохождении конвейера для каждого коммита |

### Подпись артефактов

| Вариант | Плюсы | Минусы |
|---|---|---|
| cosign (Sigstore) | Стандарт для OCI-образов | По умолчанию - журнал прозрачности и OIDC в интернете; для образов нужен реестр; на целевых системах нет cosign |
| GPG (подписанный APT-репозиторий) | Родной механизм apt | Только для пакетов; управление связкой ключей GPG; образы не покрывает |
| **Ed25519 (OpenSSL 3) над манифестом SHA256SUMS** | Работает без сети (on-premise); один механизм для пакетов, образов (архивы OCI) и SBOM; проверка штатным `openssl` и `sha256sum` на Debian 12 и Astra 1.8 | Свой формат каталога выпуска; для реестров образов и Kubernetes (вне MVP) потребуется cosign - отдельным ADR |

### Базовый образ контейнеров

| Вариант | Плюсы | Минусы |
|---|---|---|
| `debian:bookworm-slim` | Оболочка для отладки | Сотня пакетов и их уязвимости; root по умолчанию |
| `distroless/cc-debian12` | Нет оболочки, есть libgcc и libstdc++ | Несёт `libssl3`, которым платформа не пользуется (OpenSSL слинкован статически), и его уязвимости |
| **`distroless/base-nossl-debian12:nonroot` + статические libc++ и libgcc** | Только glibc; нет оболочки и OpenSSL; пользователь 65532; исполняемым файлам нужна только glibc и в пакетах, и в образах | Отладка - через отдельный debug-образ или `docker cp` |

### Время барьера push при росте кода

| Вариант | Плюсы | Минусы |
|---|---|---|
| Полный прогон на каждом push, синхронно | Просто | Время растёт с кодом (clang-tidy, четыре сборки с тестами, покрытие, бенчмарки) и блокирует работу |
| Тяжёлые этапы только ночью | Быстрый push | Ошибки санитайзеров и покрытия доходят до `master` |
| **Фоновый прогон после коммита + проверка только затронутого, полный прогон ночью и при выпуске** | Push обычно не ждёт: результат готов к его моменту; время прогона определяется размером изменения, а не кода; ничего не ускользает дольше суток | Вычисление области по графу целей; отдельный клон для фоновых прогонов (дисковое место под вторые каталоги сборки) |

### Барьер бенчмарков

Шум на стенде Docker Desktop достигает ±5% (замер шага 1.3) - это сам порог. Среднее значение даёт ложные отказы. Выбрано: минимум процессорного времени по 10 повторам; при подозрении на регрессию - до двух перезапусков со слиянием по минимуму. Перезапуски могут только уменьшить минимум текущей версии, поэтому настоящая регрессия не маскируется, а случайный выброс отсеивается.

## Решение

1. **Конвейеры** - задачи корневого Taskfile, барьеры [strategy.md](../quality/strategy.md#4-барьеры):
   - `task ci` - барьер каждого push: сборка с `-Werror` во всех пресетах, fitness functions, формат, clang-tidy, unit-тесты, ASan+UBSan, TSan, покрытие, запуск на Debian 12 и Astra 1.8, контракты, документация, `security:deps`, `bench:compare`, установка пакетов, проверка образов - в области изменения (п. 2). `FULL=true` - полная область. Интеграционные тесты против локального окружения добавляются на шаге 1.4;
   - `task ci:nightly` - `ci` в полной области, воспроизводимость сборки, сканирование образов;
   - `task release` - `ci:nightly`, подписанный каталог выпуска, его проверка.
2. **Область push** (`tools/ci/scope.py`, `scope.yaml`): изменения - рабочее дерево против базы слияния с `origin/master`. Затронутые цели - цели изменённых модулей и все цели, транзитивно зависящие от них (граф CMake File API). Сборка всегда полная и инкрементальная; выборочно выполняются дорогие этапы: clang-tidy - единицы трансляции затронутых целей, тесты и санитайзеры - тесты этих целей (метка ctest с именем цели), покрытие - их модули, бенчмарки - затронутые. Контракты, полная проверка документации, проверка зависимостей, пакеты и образы включаются по изменённым путям. Изменение сборочной инфраструктуры (CMake, Conan, профили, правила линтера и формата, Taskfile, toolchain) или отсутствие `origin/master` дают полную область.
3. **Фоновый прогон.** Хук `post-commit` запускает `tools/ci/runner.sh` в фоне: конвейер проверяет ровно закоммиченное содержимое в постоянном клоне `.cache/ci/repo` (свои каталоги сборки - инкрементальные прогоны; общие кэши Conan, ccache, Trivy), с 8 параллельными заданиями, чтобы стенд оставался отзывчивым. Одновременно идёт один прогон; запрос для коммита, который уже не HEAD, пропускается. Итог - `.cache/ci/<commit>.ok` или `.failed` с журналом и уведомлением рабочего стола (`task ci:status`, `task ci:log`, `task ci:run`).
4. **Барьер push.** Хук `pre-push` пропускает коммит с записью `.ok`, дожидается идущего прогона, а при отсутствии записи запускает его сам (в клоне, поэтому незакоммиченные правки не мешают). Обход `--no-verify` - только в аварийных случаях, коммит без записи виден (`task ci:status SHA=<commit>`).
5. **Пакеты** - CPack DEB (`cmake/PsimPackaging.cmake`): пакет `psim-<компонент>` на устанавливаемый компонент, зависимость только `libc6 (>= 2.36)`, один пакет для Debian 12 и Astra 1.8, время файлов фиксировано. Исполняемые файлы компонуют libc++, libc++abi и libgcc статически (дополнение к ADR-032). `task release:package:test` ставит, запускает и удаляет пакеты в чистых образах обеих платформ.
6. **Образы** - `deploy/images/<имя>/Dockerfile` на `distroless/base-nossl-debian12:nonroot` по дайджесту, пользователь 65532, метки OCI (версия, коммит). `task release:images:test` проверяет запуск с `--read-only`, `--cap-drop ALL`, `no-new-privileges` и не под root.
7. **SBOM** - CycloneDX 1.6 (`tools/release/sbom.py`): компоненты приложения - зависимости Conan контекста host без тестовых (gtest, benchmark объявлены `test_requires`) и статически скомпонованная libc++, граф зависимостей - из Conan; на каждый артефакт выпуска - свой SBOM с SHA-256 артефакта; для образа добавляются пакеты ОС из сканирования Trivy. Время SBOM - время коммита, серийный номер - из содержимого.
8. **Уязвимости и лицензии** (Trivy 0.75, ADR-031): `security:deps` - `conan.lock` и SBOM приложения, HIGH и CRITICAL блокируют; лицензии компонентов приложения - белый список `tools/release/licenses.yaml`, компонент без лицензии или с лицензией вне списка блокирует (копилефт для статически компонуемого кода запрещён). `security:images` - образы, исправимые HIGH и CRITICAL блокируют, неисправленные видны в отчёте ночного прогона.
9. **Подпись** (`tools/release/sign.sh`, `verify.sh`): каталог выпуска `dist/psim-<версия>-<коммит>/` - пакеты, архивы образов, SBOM, `SHA256SUMS` и его подпись Ed25519 `SHA256SUMS.sig`. Проверка доверяет только ключу, полученному отдельно (`PSIM_TRUSTED_KEY` или `deploy/keys/psim-release.pub.pem`), а не ключу из каталога; требует совпадения всех сумм, отсутствия неучтённых файлов и SBOM с хэшем каждого артефакта. Установщик (шаг 9.2) выполняет тот же `verify.sh`.
10. **Ключи.** Релизный ключ создаёт владелец (`task release:keygen DIR=<защищённый каталог>`), закрытая часть хранится вне репозитория и передаётся через `PSIM_SIGNING_KEY`, открытая публикуется в `deploy/keys/psim-release.pub.pem` к первому выпуску (шаг 11.3). До этого подписывается ключ разработки `.cache/keys/psim-dev.pem`, проверка явно сообщает об этом.
11. **Закрепление (SR-23):** образы инструментов, базовые образы (toolchain, buf, golang, distroless, Trivy, целевые платформы) - тег и дайджест; зависимости C++ - `conan.lock`. Пакеты LLVM из apt.llvm.org внутри образа toolchain версий не закрепляют (репозиторий не хранит старые сборки); воспроизводимость проверяется побайтным сравнением сборок в одном образе (FF-13), образ идентифицируется хэшем Dockerfile.
12. **Бенчмарки** (`tools/bench/bench.py`, `psim_add_benchmark`): Google Benchmark в пресете `release`; базовая линия - результаты коммита слияния с `origin/master`, кэш `.cache/bench/<коммит>.json`, при отсутствии - сборка базового коммита из `git archive`; порог - 5% по минимуму CPU-времени с перезапусками.

## Последствия

- Конвейер и DoD проверяются в одной среде; push обычно не ждёт конвейер, а время прогона определяется размером изменения. Ошибка за пределами области (например, в незатронутом модуле из-за общего заголовка вне графа целей) обнаруживается не позже ночного прогона.
- Барьер на стороне клиента: дисциплина обеспечивается хуком и видимостью записей; при появлении команды или общего стенда решение пересматривается новым ADR (серверный CI).
- Окружение `E-CI` стратегии качества - это стенд разработчика, на котором выполняется `task ci`.
- Новый устанавливаемый компонент добавляет `install(... COMPONENT)`, `psim_package()`, при необходимости `deploy/images/<имя>/Dockerfile` и имя в `IMAGES`.
- Распространение образов через реестр и подпись cosign - вне MVP (Kubernetes перенесён), при необходимости - отдельный ADR.

## Проверка

`task ci`, `task ci:nightly`, `task release`; область - модульные тесты `tools/ci/test_scope.py` (в `task arch:selftest`). Отрицательные проверки шага 1.3: искусственная регрессия бенчмарка на 20%, уязвимые версии зависимостей в SBOM, запрещённая лицензия и компонент без лицензии, подмена артефакта, неучтённый файл, отсутствующий SBOM, чужой ключ, изменённый манифест - каждая даёт отказ.
