# ADR-034. Локальный конвейер CI/CD и цепочка поставки

- **Статус:** Принято
- **Дата:** 2026-10-06
- **Шаг плана:** 1.3
- **Связанные:** ADR-030, ADR-031, ADR-032, ADR-033, требования SR-23 и SR-24 ([threat-register.md](../security/threat-register.md)), [strategy.md](../quality/strategy.md#4-барьеры)

## Контекст

Шаг 1.3 требует конвейер от коммита до подписанного артефакта: сборка, статический анализ, тесты, санитайзеры, контракты, интеграционные тесты, бенчмарки, пакеты и образы, SBOM CycloneDX, проверка лицензий и уязвимостей, подпись. DoD: каждое изменение проходит полный конвейер, релизный артефакт содержит SBOM и подпись.

Решение владельца продукта (2026-10-06): конвейер выполняется локально на стенде разработчика (Docker Desktop); git-хостинг - только хранилище кода, конвейеров на хостинге нет. Разработку ведут один инженер и ИИ-агент, коммиты и push делает инженер.

Требования безопасности: SR-23 - зависимости закреплены lock-файлами, базовые образы и образы инструментов - по дайджесту, SBOM, блокирующая проверка лицензий и уязвимостей, воспроизводимые сборки; SR-24 - подпись артефактов, проверка подписи установщиком, контейнеры без root, с файловой системой только для чтения и без лишних capabilities.

## Рассмотренные варианты

### Где выполняется конвейер

| Вариант | Плюсы | Минусы |
|---|---|---|
| CI хостинга (GitHub Actions) | Барьер на стороне сервера | Противоречит решению владельца; раннеры без Docker Desktop стенда; секреты подписи на хостинге |
| Собственный CI-сервер (Jenkins, Woodpecker) на стенде | Барьер на сервере | Ещё одна система для одного инженера; дублирует то, что уже делают задачи Task |
| **Задачи Task на стенде + хук `pre-push`** | Тот же набор задач, что разработчик запускает руками (ADR-030); проверяется ровно та среда, где проверяется DoD; нет внешних систем | Барьер на стороне клиента: `--no-verify` обходит его - смягчается записью о прохождении конвейера для каждого коммита |

### Подпись артефактов

| Вариант | Плюсы | Минусы |
|---|---|---|
| cosign (Sigstore) | Стандарт для OCI-образов | По умолчанию - журнал прозрачности и OIDC в интернете; для образов нужен реестр; на целевых системах нет cosign |
| GPG (подписанный APT-репозиторий) | Родной механизм apt | Только для пакетов; управление связкой ключей GPG; образы не покрывает |
| **Ed25519 (OpenSSL 3) над манифестом SHA256SUMS** | Работает без сети (on-premise); один механизм для пакетов, образов (архивы OCI) и SBOM; проверка штатным `openssl` и `sha256sum` на Debian 12 и Astra 1.8 | Свой формат каталога выпуска; для реестров образов и Kubernetes (вне MVP) потребуется cosign - отдельным ADR |

### Базовый образ контейнеров

| Вариант | Плюсы | Минусы |
|---|---|---|
| `debian:bookworm-slim` | Оболочка для отладки | Сотня пакетов и их уязвимости; root по умолчанию |
| `distroless/cc-debian12` | Нет оболочки, есть libgcc и libstdc++ | Несёт `libssl3`, которым платформа не пользуется (OpenSSL слинкован статически), и его уязвимости |
| **`distroless/base-nossl-debian12:nonroot` + статические libc++ и libgcc** | Только glibc; нет оболочки и OpenSSL; пользователь 65532; исполняемым файлам нужна только glibc и в пакетах, и в образах | Отладка - через отдельный debug-образ или `docker cp` |

### Барьер бенчмарков

Шум на стенде Docker Desktop достигает ±5% (замер шага 1.3) - это сам порог. Среднее значение даёт ложные отказы. Выбрано: минимум процессорного времени по 10 повторам; при подозрении на регрессию - до двух перезапусков со слиянием по минимуму. Перезапуски могут только уменьшить минимум текущей версии, поэтому настоящая регрессия не маскируется, а случайный выброс отсеивается.

## Решение

1. **Конвейеры** - задачи корневого Taskfile, барьеры [strategy.md](../quality/strategy.md#4-барьеры):
   - `task ci` - барьер каждого push: `task check` (сборка с `-Werror`, clang-tidy, fitness functions, unit-тесты, ASan+UBSan, TSan, покрытие, контракты, запуск на Debian 12 и Astra 1.8, документация), `security:deps`, `bench:compare`, установка пакетов на целевых платформах, проверка образов. Интеграционные тесты против локального окружения добавляются на шаге 1.4;
   - `task ci:nightly` - `ci` плюс воспроизводимость сборки и сканирование образов;
   - `task release` - `ci:nightly`, подписанный каталог выпуска, его проверка.
2. **Барьер push.** Успешный `task ci` на чистом рабочем дереве записывает `.cache/ci/<commit>.ok`. Хук `tools/git-hooks/pre-push` пропускает только коммиты с такой записью; если отправляется HEAD чистого дерева без записи - запускает `task ci` сам. Обход `--no-verify` - только в аварийных случаях, коммит без записи виден (`task ci:status SHA=<commit>`).
3. **Пакеты** - CPack DEB (`cmake/PsimPackaging.cmake`): пакет `psim-<компонент>` на устанавливаемый компонент, зависимость только `libc6 (>= 2.36)`, один пакет для Debian 12 и Astra 1.8, время файлов фиксировано. Исполняемые файлы компонуют libc++, libc++abi и libgcc статически (дополнение к ADR-032). `task release:package:test` ставит, запускает и удаляет пакеты в чистых образах обеих платформ.
4. **Образы** - `deploy/images/<имя>/Dockerfile` на `distroless/base-nossl-debian12:nonroot` по дайджесту, пользователь 65532, метки OCI (версия, коммит). `task release:images:test` проверяет запуск с `--read-only`, `--cap-drop ALL`, `no-new-privileges` и не под root.
5. **SBOM** - CycloneDX 1.6 (`tools/release/sbom.py`): компоненты приложения - зависимости Conan контекста host без тестовых (gtest, benchmark объявлены `test_requires`) и статически скомпонованная libc++, граф зависимостей - из Conan; на каждый артефакт выпуска - свой SBOM с SHA-256 артефакта; для образа добавляются пакеты ОС из сканирования Trivy. Время SBOM - время коммита, серийный номер - из содержимого.
6. **Уязвимости и лицензии** (Trivy 0.75, ADR-031): `security:deps` - `conan.lock` и SBOM приложения, HIGH и CRITICAL блокируют; лицензии компонентов приложения - белый список `tools/release/licenses.yaml`, компонент без лицензии или с лицензией вне списка блокирует (копилефт для статически компонуемого кода запрещён). `security:images` - образы, исправимые HIGH и CRITICAL блокируют, неисправленные видны в отчёте ночного прогона.
7. **Подпись** (`tools/release/sign.sh`, `verify.sh`): каталог выпуска `dist/psim-<версия>-<коммит>/` - пакеты, архивы образов, SBOM, `SHA256SUMS` и его подпись Ed25519 `SHA256SUMS.sig`. Проверка доверяет только ключу, полученному отдельно (`PSIM_TRUSTED_KEY` или `deploy/keys/psim-release.pub.pem`), а не ключу из каталога; требует совпадения всех сумм, отсутствия неучтённых файлов и SBOM с хэшем каждого артефакта. Установщик (шаг 9.2) выполняет тот же `verify.sh`.
8. **Ключи.** Релизный ключ создаёт владелец (`task release:keygen DIR=<защищённый каталог>`), закрытая часть хранится вне репозитория и передаётся через `PSIM_SIGNING_KEY`, открытая публикуется в `deploy/keys/psim-release.pub.pem` к первому выпуску (шаг 11.3). До этого подписывается ключ разработки `.cache/keys/psim-dev.pem`, проверка явно сообщает об этом.
9. **Закрепление (SR-23):** образы инструментов, базовые образы (toolchain, buf, golang, distroless, Trivy, целевые платформы) - тег и дайджест; зависимости C++ - `conan.lock`. Пакеты LLVM из apt.llvm.org внутри образа toolchain версий не закрепляют (репозиторий не хранит старые сборки); воспроизводимость проверяется побайтным сравнением сборок в одном образе (FF-13), образ идентифицируется хэшем Dockerfile.
10. **Бенчмарки** (`tools/bench/bench.py`, `psim_add_benchmark`): Google Benchmark в пресете `release`; базовая линия - результаты коммита слияния с `origin/master`, кэш `.cache/bench/<коммит>.json`, при отсутствии - сборка базового коммита из `git archive`; порог - 5% по минимуму CPU-времени с перезапусками.

## Последствия

- Конвейер и DoD проверяются в одной среде; полный `task ci` занимает минуты при тёплых кэшах.
- Барьер на стороне клиента: дисциплина обеспечивается хуком и видимостью записей; при появлении команды или общего стенда решение пересматривается новым ADR (серверный CI).
- Окружение `E-CI` стратегии качества - это стенд разработчика, на котором выполняется `task ci`.
- Новый устанавливаемый компонент добавляет `install(... COMPONENT)`, `psim_package()`, при необходимости `deploy/images/<имя>/Dockerfile` и имя в `IMAGES`.
- Распространение образов через реестр и подпись cosign - вне MVP (Kubernetes перенесён), при необходимости - отдельный ADR.

## Проверка

`task ci`, `task ci:nightly`, `task release`. Отрицательные проверки шага 1.3: искусственная регрессия бенчмарка на 20%, уязвимые версии зависимостей в SBOM, запрещённая лицензия и компонент без лицензии, подмена артефакта, неучтённый файл, отсутствующий SBOM, чужой ключ, изменённый манифест - каждая даёт отказ.
