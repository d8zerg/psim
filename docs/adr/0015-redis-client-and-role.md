# ADR-015. Redis-совместимое хранилище, клиент и его роль

- **Статус:** Предложено (принимается в начале шага 2.5)
- **Дата:** 2026-10-06
- **Шаг плана:** 2.5
- **Связанные:** ADR-016, ADR-018, [deployment.md](../architecture/deployment.md#3-топология-кластер-на-vm)

## Контекст

Redis используется для реестра сессий коннекторов, ограничения частоты запросов и горячих проекций (лента). План называет Redis Cluster. С 2024 года Redis распространяется под RSALv2/SSPL, с версии 8 - также под AGPLv3; поставка в составе коммерческого продукта on-premise под такими лицензиями нежелательна (ограничение «только открытые лицензии, допускающие поставку»).

## Рассмотренные варианты

### Сервер

| Вариант | Плюсы | Минусы |
|---|---|---|
| Redis 7.4+ / 8 | Оригинал | RSALv2/SSPL/AGPL - ограничения при поставке |
| **Valkey** (форк Redis 7.2, BSD-3, Linux Foundation) | Открытая лицензия, совместимость протокола, активное развитие | - |
| KeyDB, Dragonfly | Производительность | Dragonfly - BSL; KeyDB развивается слабо |

### Топология

| Вариант | Плюсы | Минусы |
|---|---|---|
| Redis Cluster (шардирование, план) | Масштаб по объёму | Объём данных MVP - мегабайты; клиент должен поддерживать маршрутизацию по слотам и перенаправления; многоключевые операции ограничены |
| **Primary + 2 реплики под Sentinel** | Достаточно для объёма MVP; простой клиент; автоматическое переключение | Нет горизонтального масштаба записи (не требуется) |

### Клиент

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Boost.Redis** | Asio-нативный, корутины, RESP3, конвейеризация | Поддержку Sentinel и Cluster нужно проверить для выбранной версии Boost; при отсутствии - тонкий слой обнаружения мастера |
| redis-plus-plus (hiredis) | Cluster и Sentinel | Асинхронный режим на libuv - чужой цикл событий |

## Предлагаемое решение

1. Сервер - **Valkey**; в кластере - primary + 2 реплики под управлением Sentinel (3 экземпляра Sentinel на узлах инфраструктуры); на одной машине - один экземпляр. Отличие от плана (Redis Cluster) - из-за объёма данных MVP; переход на Valkey Cluster возможен без изменения сервисов, если клиент инкапсулирует топологию.
2. Клиент - Boost.Redis за портом `libs/platform/redis`; обнаружение мастера через Sentinel - в слое платформы, если не поддерживается клиентом.
3. **Роль:** Redis - не источник истины. Всё, что в нём хранится, восстановимо: реестр сессий - переподключением коннекторов, проекции - из Kafka и PostgreSQL, счётчики лимитов - допускают сброс. Потеря Redis деградирует функции, но не теряет данные.

## Последствия

- Документы развёртывания обновляются при принятии ADR в шаге 2.5 (сейчас в [deployment.md](../architecture/deployment.md) описан кластерный вариант плана).
- Сервисы проверяются на работу при недоступности Redis (деградация, а не отказ обработки событий).

Интеграционные тесты переключения мастера под нагрузкой (DoD шага 2.5); хаос-тест отказа узла Redis (S11).
