## 0. Назначение и допущения

Документ определяет пошаговый план разработки MVP вендор-нейтральной Enterprise-платформы PSIM. Для каждого шага указаны цель, входной контекст, работы, результат, критерии готовности (DoD) и зависимости.

### 0.1 Зафиксированные решения

| Область | Решение |
|---|---|
| Продукт | Вендор-нейтральная PSIM-платформа для любых организаций и интеграторов |
| Редакция | Одна - Enterprise. Профилей и урезанных редакций нет |
| Топологии | Одна машина -> кластер на VM -> Kubernetes. Сборки и функциональность одинаковы, различаются конфигурация и число экземпляров |
| Поставка | DEB-пакеты и контейнерные образы для самостоятельного развёртывания в локальной или облачной инфраструктуре |

| Сборка | CMake + Ninja, Conan 2, clang toolchain, clang-tidy, санитайзеры |
| Тесты сервера | GoogleTest/GMock, Google Benchmark, libFuzzer |
| Наблюдаемость | OpenTelemetry (OTLP), Prometheus, Grafana, сбор логов и трассировок |
| Identity Provider | Keycloak (OIDC/OAuth2) |
| Веб-клиент | React 19, TypeScript, Vite, TanStack Query/Router, Zustand, Tailwind CSS 4, shadcn/ui, Vitest, Playwright; монорепозиторий pnpm + Turborepo |

| Retention | Настраивается по уровням топиков; для PoC - короткий |
| ИИ | Ассистент с источниками и без выполнения действий - ADR-067; автоматические решения вне MVP |

### 0.2 Допущения

1. **Кодовая база новая.** Из прежних наработок PSIM Server после ревизии переносятся только инфраструктурные части: сборка, каркас сервиса, наблюдаемость, веб-оболочка. Доменная часть пишется заново под вендор-нейтральную модель и Kafka.
2. **План рассчитан на ведущего инженера с возможностью подключить команду.** Шаги декомпозированы так, чтобы допускать параллельную работу. Организация работ и критический путь приведены в разделе 19.
3. **Публичное название - Open-Source PSIM Platform (Q4 закрыт).** Репозиторий, код, пространства имён и префиксы контрактов - `psim`; техническое название стенда, образов сборки и поставки - `psim-platform`.
4. **Мультитенантность.** В MVP эксплуатируется один тенант, но идентификатор тенанта присутствует в модели данных, контрактах и ключах с первого дня.

## 1. Цели MVP

### 1.1 Продуктовая цель

Полноценный сквозной контур управления ситуациями: событие от любого источника -> нормализация -> корреляция -> инцидент -> сценарий реагирования -> команды на устройства -> закрытие -> аудит и отчётность. Работа идёт через веб-консоль оператора и веб-администрирование при нагрузке 50 000 событий/с.

### 1.2 Ключевые сценарии приёмки

| № | Сценарий |
|---|---|
| S1 | Интегратор подключает новый коннектор, регистрирует его в каталоге и получает поток событий без изменения ядра |
| S2 | Администратор описывает объект (площадка, здание, этаж, зона), импортирует устройства и привязывает источники к зонам |
| S3 | Событие датчика нормализуется, обогащается контекстом объекта и попадает в обработку |
| S4 | Правило корреляции связывает события нескольких источников в окне времени и порождает сигнал |
| S5 | Сигнал создаёт инцидент или присоединяется к открытому; дубликаты не создаются ни при каких сбоях |
| S6 | Инцидент появляется в консоли оператора не позже чем через 1 с от события (p99) со звуковым и визуальным оповещением |
| S7 | Оператор принимает инцидент и выполняет сценарий реагирования: шаги, чек-листы, решения, обязательные действия |
| S8 | Оператор отправляет команду на устройство и получает подтверждение исполнения или отказ по таймауту |
| S9 | Отсутствие реакции в пределах SLA запускает эскалацию и уведомления |
| S10 | Все действия пользователей и системы фиксируются в аудите с защитой от модификации |
| S11 | Отказ брокера Kafka или экземпляра сервиса не приводит к потере событий и инцидентов |
| S12 | Обновление версии в кластерной топологии выполняется без остановки обработки; нагрузочная квалификация опциональна |
| S13 | Руководитель получает отчёт по инцидентам: количество, MTTA, MTTR, доля ложных тревог |

### 1.3 Нефункциональные цели (SLO MVP)

| Атрибут | Цель |
|---|---|
| Пропускная способность | 50 000 событий/с устойчиво в течение 10 мин, пиковый ×1,5 в течение 5 мин |
| Задержка событие -> сигнал | p99 ≤ 300 мс |
| Задержка событие -> инцидент в консоли | p99 ≤ 1 с |
| Задержка отклика REST API | p99 ≤ 200 мс для операций чтения консоли |
| Потери данных | 0 событий, 0 инцидентов (проверяется сквозной сверкой последовательностей) |
| Дубликаты инцидентов | 0 при любых перезапусках и повторах |
| RTO, кластерная топология | ≤ 60 с при отказе любого одного узла |
| RPO для инцидентов | 0 в кластерной топологии |
| Обновление | Без простоя обработки в кластерной топологии; квалификация S12/C-12 опциональна |
| Консоль | Плавная работа ленты с 10 000 активных инцидентов |

### 1.4 Цели инженерного качества

| Показатель | Цель |
|---|---|
| Предупреждения компилятора и clang-tidy | 0 (`-Werror`) |
| Санитайзеры (ASan, UBSan, TSan) | Обязательны в CI, 0 срабатываний |
| Покрытие доменного ядра | ≥ 90% строк, ≥ 80% ветвей |
| Покрытие инфраструктурного кода | ≥ 75% |
| Фаззинг | На шаге 5.1 - парсер и валидатор правил без падений за 10 мин; на шаге 10.3 - все внешние парсеры и DSL правил без падений за 24 ч |
| Совместимость контрактов | Автоматическая проверка в CI, без ручных исключений |
| Регрессия производительности | Автоматический барьер в CI: падение > 5% блокирует слияние |
| Сборки | Воспроизводимые, с SBOM и подписанными артефактами |
| Документация | Самодостаточная документация конечного состояния платформы: архитектура (arc42 + C4), ADR, руководства и API-справочники; EN по умолчанию и полная версия RU |

## 2. Принципы инженерного исполнения

Эти принципы определяют, как выполняется каждый шаг, и составляют основу инженерного уровня продукта.

1. **Сначала архитектура, все решения фиксируются.** Значимые решения оформляются как ADR до реализации. Архитектура описана по arc42 с диаграммами C4.
2. **Контракты прежде реализации.** Схемы событий (Protobuf), топики (AsyncAPI), REST (OpenAPI) и протокол коннекторов (gRPC) - версионируемые публичные артефакты. Совместимость проверяется в CI.
3. **Гексагональная архитектура.** Доменное ядро не зависит от Kafka, PostgreSQL, Redis, сети и часов. Инфраструктура подключается через порты и адаптеры.
4. **Детерминированное ядро.** Время, случайность и ввод-вывод абстрагированы. Это позволяет детерминированное симуляционное тестирование всего конвейера.
5. **Явная семантика доставки.** Для каждого потока определены at-least-once или exactly-once, ключ партиционирования, порядок, идемпотентность и поведение при повторах.
6. **Воспроизводимость.** Любая read-модель восстанавливается проигрыванием Kafka. Правила можно прогнать по историческим данным.
7. **Наблюдаемость с первого шага.** Сквозная трассировка от датчика до действия оператора, метрики «золотых сигналов» и бизнес-метрики в каждом сервисе.
8. **Безопасность по умолчанию.** TLS везде, mTLS для коннекторов, проверка токенов на каждом входе, минимальные привилегии, аудит.
9. **Производительность как требование.** Бюджет задержек на каждый этап, бенчмарки и нагрузочные тесты в CI, профилирование до оптимизации, дисциплина аллокаций.
10. **Fitness functions.** Архитектурные правила проверяются автоматически: направления зависимостей, запрет инфраструктуры в домене, совместимость схем, бюджеты задержек.
11. **Документация как код.** Документация лежит рядом с кодом, собирается в CI и проверяется на актуальность.
12. **Ранняя проверка сквозного потока.** Минимальный поток собирается как можно раньше, затем его функциональность расширяется.

## 3. Целевая архитектура MVP

### 3.1 Логические компоненты

| Компонент | Ответственность | Хранилище |
|---|---|---|
| Connector SDK | Библиотека для разработки коннекторов: протокол, буферизация, повторы, команды | - |
| Connector Gateway | Приём подключений коннекторов (gRPC, mTLS), аутентификация, валидация, rate limiting, запись в Kafka, доставка команд | Redis (реестр сессий) |
| Resource Catalog | Объекты, зоны, устройства, источники, типы, возможности; публикация в compacted-топик | PostgreSQL |
| Normalizer | Приведение сырых событий к единой таксономии, обогащение контекстом каталога, отбраковка в DLQ | Локальный кэш каталога |
| Correlation Engine | Правила, окна, последовательности, пороги, отсутствие событий; генерация сигналов | RocksDB + changelog в Kafka |
| Incident Service | Жизненный цикл инцидентов, группировка сигналов, приоритеты, назначение, хронология | PostgreSQL + outbox/inbox |
| Response Engine | Исполнение сценариев реагирования (SOP), таймеры, эскалации | PostgreSQL |
| Command Service | Жизненный цикл команд на устройства, подтверждения, таймауты | PostgreSQL |
| Notification Service | Уведомления в приложении, по email и через webhook | PostgreSQL + outbox |
| Projection Service | Read-модели: лента инцидентов, состояние объектов и устройств; факты инцидентов для отчётов | Redis, PostgreSQL, ClickHouse |
| Event History | Загрузка всех нормализованных событий и их связей с сигналами, поиск для разбора инцидентов, статистика правил | ClickHouse |
| Audit Service | Неизменяемый журнал с защитой от модификации (hash chain) | PostgreSQL |
| API Gateway | REST v1, WebSocket realtime, проверка токенов, авторизация, лимиты | Redis |
| Web Application | Консоль оператора и администрирование в одном приложении с ролевыми модулями | - |

Компоненты собираются как независимые сервисы из одного монорепозитория. В топологии «одна машина» запускаются тем же набором контейнеров или systemd-юнитов, что и в кластере.

### 3.2 Потоки Kafka

| Уровень | Топик | Ключ | Семантика | Retention |
|---|---|---|---|---|
| Ввод | `psim.ingest.raw.v1` | source_id | at-least-once | Короткий (часы) |
| Нормализация | `psim.events.normalized.v1` | site_id + zone_id | at-least-once, идемпотентно по event_id | Настраиваемый |
| Корреляция | `psim.signals.v1` | correlation_key | exactly-once (транзакции Kafka) | Настраиваемый |
| Инциденты | `psim.incidents.events.v1` | incident_id | exactly-once через outbox | Длительный |
| Реагирование | `psim.response.events.v1` | incident_id | через outbox | Длительный |
| Команды | `psim.commands.v1` | connector_id | at-least-once, идемпотентно по command_id | Короткий |
| Результаты команд | `psim.commands.results.v1` | command_id | at-least-once | Короткий |
| Каталог | `psim.catalog.v1` | resource_id | compacted | Бессрочно |
| Конфигурация | `psim.config.v1` | config_key | compacted | Бессрочно |
| Аудит | `psim.audit.v1` | tenant_id | at-least-once, идемпотентно | Длительный |
| Состояние корреляции | `psim.correlation.changelog.v1` | state_key | compacted | Бессрочно |
| Ошибки | `psim.dlq.<stage>.v1` | исходный ключ | at-least-once | Длительный |

Именование топиков: `<продукт>.<домен>.<сущность>.<версия>`. Все сообщения содержат единый конверт: event_id (UUIDv7), tenant_id, тип и версию схемы, время возникновения, время приёма, контекст трассировки, порядковый номер у источника и полезную нагрузку.

### 3.3 Хранение событий

Решение - [ADR-028](adr/0028-clickhouse-analytical-storage.md) (заменяет ADR-013).

- Сырые и нормализованные события хранятся в Kafka в пределах retention топиков.
- Все нормализованные события загружаются в ClickHouse (таблица `events`) сервисом Event History; там же - связи событий с сигналами (`event_signals`) и статистика сигналов (`signal_facts`). Retention - TTL по уровням: все события 7 суток, значимые события и связи 90 суток (по умолчанию, задаётся в `RetentionSettings`).
- Факты жизненного цикла инцидентов (`incident_facts`) загружает Projection Service; на них строятся отчёты (MTTA, MTTR, ложные тревоги, SLA), retention 400 суток.
- ClickHouse - не источник истины: таблицы восстанавливаются проигрыванием Kafka в пределах retention или пересчётом из PostgreSQL. Агрегаты предметной области, outbox, inbox и аудит остаются в PostgreSQL.
- Загрузка - пакетная вставка по нативному протоколу с токеном дедупликации; смещение Kafka фиксируется после успешной вставки. Replicated-движки и ClickHouse Keeper во всех топологиях.

- **DoD:** найденная ошибка воспроизводится по зерну; ручной короткий прогон выполняет 200 сценариев, длинный - 10 000. До появления доменного конвейера проверяется эталонная цепочка доставки; подключение предметной логики - шаг 5.2.
- **Зависимости:** 2.2.

### Шаг 2.8 Слой ClickHouse

- **Цель:** надёжная загрузка потоков Kafka в ClickHouse и быстрые аналитические запросы для истории событий и отчётов.
- **Вход:** ADR-028, ADR-045, 2.2, 2.3, 2.4.
- **Работы:**
  - Клиент нативного протокола (clickhouse-cpp) с TLS; интеграция с Asio через пул блокирующих операций из 2.2; пул соединений и переключение между репликами.
  - Шаблон загрузчика «Kafka -> ClickHouse»: пакеты по размеру и времени, противодавление, фиксация смещений только после успешной вставки, токен дедупликации вставки (топик, партиция, диапазон смещений), DLQ для непреобразуемых записей.
  - Устойчивый журнал незавершённых пакетов в PostgreSQL с исходными байтами и границами; восстановление до обработки новых пакетов, транзакционная DLQ вместе со смещениями (ADR-045).
  - Преобразование Protobuf-сообщений в столбцовые блоки без промежуточных копий.
  - Построитель запросов только с параметрами (SR-13); обязательные `tenant_id` и интервал времени в каждом запросе (ADR-022); ограничения на время выполнения и объём результата.
  - Миграции DDL по правилам expand/contract (ADR-024) для Replicated-движков; одинаковые DDL для всех топологий.
  - Метрики: размер и задержка пакетов, отставание загрузки от Kafka, ошибки вставки, длительность запросов.
- **Результат:** библиотека ClickHouse и шаблон загрузчика.
- **DoD:**
  - принудительное падение между вставкой и фиксацией смещения не даёт ни потерь, ни дубликатов (сверка числа строк и идентификаторов);
  - бенчмарк загрузки ≥ 100 000 строк/с на один экземпляр на эталонном стенде;
  - компонентные тесты против контейнера окружения 1.4, включая отказ и возврат реплики.
- **Зависимости:** 2.2, 2.3, 2.4, 1.4.


### Шаг 2.9 Слой S3-совместимого объектного хранилища

- **Цель:** общий инфраструктурный слой хранения объектов для поэтажных планов и последующих файловых функций.
- **Вход:** ADR-042, ADR-046, 2.2, 2.6, локальное окружение 1.4.
- **Работы:**
  - Выбор C++ SDK и одной реализации S3-совместимого хранилища для MVP; фиксация в ADR лицензий, версий, возможностей, установки на Debian 13 x86_64 и поддержки одной машины и кластера.
  - Библиотека `libs/platform/s3`: загрузка, скачивание, получение метаданных и удаление объектов; интеграция с асинхронной моделью 2.2 без блокировки потоков исполнения.
  - Потоковая передача с ограничением памяти и размера объекта, таймауты и отмена операций; ограниченные повторы только при безопасной семантике операции, включая неизвестный результат загрузки после сетевого разрыва.
  - TLS с проверкой сервера и секреты через механизмы 2.6; закрытый bucket и минимальные права технической учётной записи.
  - Единые ошибки и метрики длительности, объёма передачи, повторов и отказов; исключение секретов из журналов.
  - Проверка целостности по SHA-256; ETag не считается эквивалентом SHA-256. Версии планов определяются в Resource Catalog независимо от поддержки версионирования объектов хранилищем.
  - Добавление хранилища в локальное окружение и компонентные тесты; описание конфигурации и требований для поставки 9.1 и резервного копирования 9.3.
- **Результат:** библиотека S3, ADR выбора SDK и хранилища, локальное тестовое окружение и документация интеграции.
- **DoD:**
  - загрузка и скачивание объектов до 20 МБ, чтение метаданных и удаление проверены на выбранном хранилище; содержимое сверяется по SHA-256;
  - негативные компонентные тесты проверяют отсутствие объекта, отказ доступа, неверный сертификат, таймаут, отмену, сетевой разрыв и восстановление;
  - передача соблюдает настроенные ограничения памяти и размера, частичный результат не выдаётся за успешный; тесты повторов проверяют поведение при неизвестном результате загрузки;
  - права Resource Catalog, валидация изображений, метаданные и версии планов реализуются в 4.4; резервное копирование и восстановление проверяются в 9.3.
- **Зависимости:** 2.2, 2.6, 1.4.

## 9. Ф4. Ввод событий и каталог ресурсов

### Шаг 4.1 Connector SDK

Реализация и проверка: [руководство SDK](engineering/connector-sdk.md), [ADR-048](adr/0048-connector-sdk.md).

- **Цель:** интеграторы подключают любые источники без изменения ядра.
- **Вход:** протокол коннекторов (0.5), 3.1.
- **Работы:**
  - Библиотека для C++: подключение, регистрация, heartbeat.
  - Локальный буфер на диске при потере связи с досылкой.
  - Управление потоком.
  - Приём и исполнение команд.
  - Метрики и диагностика.
  - Тестовый набор соответствия протоколу (conformance kit).

### Шаг 4.2 Connector Gateway

- **Цель:** надёжный и масштабируемый приём событий.
- **Вход:** 4.1, 2.6.
- **Работы:**
  - Терминирование mTLS, аутентификация коннектора и проверка его регистрации.
  - Валидация схемы, лимиты на коннектор.
  - Подтверждение коннектору только после подтверждения записи в Kafka.
  - Реестр сессий в Redis.
  - Маршрутизация команд к нужной сессии.
  - Горизонтальное масштабирование экземпляров.
  - Наблюдение за heartbeat, потерей связи и повторным подключением; публикация изменений доступности и запуск сверки состояния.
  - Ротация зарегистрированных сертификатов с перекрытием; отзыв закрывает открытые сессии и блокирует новые.
- **Результат:** сервис Connector Gateway.
- **DoD:** 50 000 событий/с через два экземпляра шлюза; падение экземпляра не теряет событий, коннекторы переподключаются автоматически.

### Шаг 4.3 Эталонные коннекторы

- **Результат:** симулятор и Webhook/HTTP-коннектор с документацией.
- **DoD:** каждый проходит тестовый набор соответствия; симулятор генерирует 75 000 событий/с с одной машины.

Реализация: [ADR-051](adr/0051-resource-catalog.md), [руководство](engineering/resource-catalog.md), `services/resource-catalog`.

- **Цель:** модель защищаемых объектов и устройств.

- **Работы:**

  - Массовый импорт и экспорт.

  - Разовые MaintenanceWindow для устройства или зоны: начало, обязательный срок окончания, причина, ответственный и явная политика подавления; изменения публикуются в конфигурационном потоке.

- **Результат:** сервис каталога.
- **DoD:** импорт 50 000 устройств не дольше 5 минут; изменения доходят до потребителей не дольше 2 секунд.

- **Зависимости:** 3.1, 2.4, 2.9.

### Шаг 4.5 Normalizer

Реализация: [ADR-052](adr/0052-normalization-and-event-history.md), [руководство](engineering/normalization-and-history.md), `services/normalizer`, `services/event-history`.

- **Цель:** единое представление событий от любых источников.

**Веха M2:** ввод, нормализация и обогащение подтверждены на 50 000 событий/с без потерь.

## 10. Ф5. Корреляция и инциденты

### Шаг 5.1 Модель и язык правил

- **Цель:** выразительные, проверяемые и безопасные правила корреляции.
- **Вход:** 0.2, ADR по языку правил.
- **Работы:**
  - Декларативная модель правил: условия, окна, последовательности, пороги, отсутствие ожидаемого события, связь нескольких источников, подавление, вычисление приоритета.
  - Валидация, версионирование и жизненный цикл: черновик -> тест -> активно -> архив.
  - Пробный прогон на исторических данных из Kafka и истории событий ClickHouse.
  - Публикация активного набора через конфигурационный топик.
  - Явная политика обслуживания: подавление только выбранных правил или типов, сохранение истории; пожарные события и P1 не подавляются.
  - Изолированный пробный прогон с отдельными результатами и ACL; отсутствие записи в рабочие сигналы, инциденты, команды и уведомления.
- **Результат:** модель правил, валидатор, сервис управления правилами.
- **DoD:** все типовые сценарии из 0.1 выражаются правилами; некорректное правило невозможно активировать; парсер и валидатор проходят 10 минут фаззинга без падений. Прогон 24 часа не является условием завершения этого шага и выполняется на шаге 10.3.
- **Дополнение к DoD (ADR-042):** при обслуживании подавленные события сохранены и объяснимы; диагностический прогон не меняет рабочие данные и не вызывает внешние системы.
- **Зависимости:** 4.5.

### Шаг 5.2 Correlation Engine

- **Цель:** корреляция с сохранением состояния, масштабируемая и восстанавливаемая.
- **Вход:** 5.1, ADR по хранению состояния корреляции.
- **Работы:**
  - Параллельная обработка по партициям.
  - Локальное состояние в RocksDB с changelog-топиком и восстановлением при переназначении партиций.
  - Семантика event time: водяные знаки, допустимое опоздание, контроль рассинхронизации часов.
  - Детерминированные идентификаторы сигналов.
  - Exactly-once через транзакции Kafka по схеме «чтение - обработка - запись».
  - Атомарное применение новой версии правил.
  - Применение версий MaintenanceWindow и качества состояния при вычислении сигналов; неизвестное состояние не считается нормальным.
- **Результат:** сервис корреляции.
- **DoD:**
  - 50 000 событий/с на трёх экземплярах при p99 ≤ 100 мс на этапе;
  - симуляционные тесты подтверждают отсутствие потерь и дубликатов сигналов при падениях и ребалансировках;
  - восстановление состояния после падения не дольше 30 секунд.
- **Дополнение к DoD (ADR-042):** границы обслуживания воспроизводимы; открытые инциденты и их SLA не меняются при подавлении новых сигналов.
- **Зависимости:** 5.1, 2.7.

### Шаг 5.3 Incident Service

Реализация: [ADR-053](adr/0053-incident-service.md), [руководство](engineering/incident-service.md).

- **Цель:** центральный агрегат продукта.
- **Вход:** 0.2, 5.2, ADR-008, ADR-020, ADR-027.
- **Работы:**
  - Принятие ADR-020 и общая библиотека авторизации `libs/platform/authz`: единая точка принятия решений по роли, тенанту, площадке и зоне из проверенного JWT; отказ с кодом каталога ошибок и событием аудита. Incident Service - первый потребитель; каталог и правила переводятся на библиотеку в 7.4.
  - Замена минимальной реализации M1 с сохранением контракта `psim.incidents.events.v1`, схемы через expand/contract и сквозного теста M1.
  - Конфигурация типов инцидентов: отображение типа сигнала в тип инцидента, ключ и окно группировки, матрица приоритета; версии публикуются в `psim.config.v1`, версия фиксируется в инциденте.
  - Жизненный цикл: новый -> принят -> в работе -> решён -> закрыт, а также эскалирован и ложный (ADR-027).
  - Группировка сигналов в открытый инцидент по ключу и окну.
  - Приоритеты и их пересчёт.
  - Назначение и передача между операторами.
  - Хронология, комментарии, вложения-ссылки (URL с проверкой схемы `https`; собственное хранение файлов - X18).
  - Идемпотентный приём сигналов через inbox, публикация изменений и записей аудита через outbox.
  - Оптимистичная конкурентность.
  - API команд инцидента (принять, назначить, комментировать, решить, закрыть, отметить ложным, передать) по контракту REST v1; внешняя маршрутизация - 7.1.
  - Передача незакрытых инцидентов: запрос, подтверждение получателя, проверка версии, прав и области; пакетная операция с результатом по каждому инциденту.
  - Допустимость получателя определяется ролью, областью доступа и активностью учётной записи; сетевое присутствие в консоли не требуется и не является условием передачи.
  - До подтверждения сохраняется прежний ответственный; передача не сбрасывает SLA и не перезапускает сценарий.
  - Предметные сценарии группировки и повторной доставки сигналов в ручном стенде `libs/sim`.
- **Результат:** сервис инцидентов, библиотека авторизации, конфигурация типов инцидентов.
- **DoD:** инварианты агрегата покрыты тестами на основе свойств; ноль дубликатов при любых повторах, SIGKILL и ребалансировке; release-замер на двух экземплярах подтверждает p99 обработки сигнала ≤ 50 мс; сквозной сценарий M1 проходит без изменения внешнего контракта.
- **Дополнение к DoD (ADR-042):** повтор передачи идемпотентен; конфликт версии и неподходящий получатель отклоняются; передача и принудительное переназначение видны в аудите.
- **Зависимости:** 5.2, 2.4.

### Шаг 5.4 Event History и связь с инцидентами

Реализация: [ADR-054](adr/0054-event-history-links.md), [руководство](engineering/event-history.md).

- **Цель:** полный контекст инцидента для разбора.
- **Вход:** 4.5, 5.3.
- **Работы:**
  - Загрузка связей событий с сигналами (`event_signals`) и статистики сигналов (`signal_facts`) из `psim.signals.v1` в ClickHouse.
  - Связь инцидента с сигналами и исходными событиями.
  - Поиск событий по объекту, зоне, устройству, типу и времени (EventHistoryService), всегда в пределах тенанта и интервала.
  - Статистика срабатываний правил для их настройки.
  - Удаление по retention через TTL ClickHouse; продление хранения значимых событий и связей.
  - Загрузчики добавляются в существующий сервис Event History (4.5) на шаблоне 2.8; поиск применяет библиотеку авторизации 5.3.
- **Результат:** API истории, связей и статистики правил.
- **DoD:** поиск за сутки по зоне ≤ 500 мс при полной нагрузке записи; связи сверены с сигналами по идентификаторам без потерь и логических дубликатов после SIGKILL загрузчика.
- **Зависимости:** 5.3.

**Веха M3:** конвейер от события до инцидента завершён и устойчив к сбоям.

## 11. Ф6. Реагирование, команды, эскалации, аудит

### Шаг 6.1 Response Engine

- **Цель:** исполнимые сценарии реагирования вместо статических инструкций.
- **Вход:** 0.2, 5.3, 6.2, ADR-012 (принимается в начале шага).
- **Работы:**

  - Привязка сценариев к типам инцидентов, зонам и приоритетам.

  - Сервис таймеров.
  - Автоматические шаги.
  - Фиксация каждого действия.

- **Дополнение к DoD (ADR-042):** исполнитель replay не имеет прав на рабочие топики и внешние вызовы; тест истории с командами и уведомлениями показывает 0 побочных эффектов.

### Шаг 6.2 Command Service

Реализация: [ADR-055](adr/0055-command-service.md), [руководство](engineering/command-service.md).

Выполняется до 6.1: шаг сценария «команда» использует этот сервис.

- **Цель:** управляемое воздействие на устройства.
- **Вход:** 4.2, 5.3, ADR-018.
- **Работы:**
  - Жизненный цикл команды: запрошена -> отправлена -> подтверждена -> исполнена, либо ошибка или таймаут.
  - Авторизация на уровне команды и области доступа через библиотеку 5.3; проверка возможности устройства по каталогу.
  - Обязательное подтверждение для критичных команд; запрет самоподтверждения.
  - Идемпотентность по идентификатору команды.
  - Маршрутизация через шлюз; неопределённый исход после разрыва сессии фиксируется отдельным статусом без автоматического повтора действия (согласовано с поведением SDK 4.1).
  - Связь команды с инцидентом и записью хронологии.
- **Результат:** сервис команд.
- **DoD:** повтор команды не приводит к двойному исполнению; каждая команда завершается финальным статусом; release-замер подтверждает p99 от запроса до доставки коннектору ≤ 200 мс.

### Шаг 6.3 Эскалации и уведомления

Реализация: [ADR-056](adr/0056-sla-and-notifications.md), [руководство](engineering/notifications.md).

- **Цель:** гарантированная реакция в рамках SLA.
- **Вход:** 6.1.
- **Работы:**
  - Политики SLA на принятие и решение.
  - Многоуровневые эскалации.
  - Каналы: в приложении, email, webhook.
  - Контракт запросов уведомлений и квитанций доставки; идентификатор уведомления исключает повторную отправку после перезапуска.
  - Повторы и фиксация доставки.
  - Подавление уведомлений при массовых событиях.
  - Email через SMTP с обязательным TLS; webhook с подписью HMAC, ограничением размера и времени, разрешённым списком адресатов и запретом адресов внутренних сетей платформы (защита от SSRF).
  - Тестовый SMTP-сервер и webhook-приёмник в локальном окружении для компонентных и сквозных проверок.
  - Явное назначение текущего дежурного площадки, разрешение получателя при отправке эскалации; резервный контакт и алерт при отсутствии дежурного.
- **Результат:** сервис уведомлений, политики эскалации.
- **DoD:** нарушение SLA гарантированно порождает эскалацию; доставка фиксируется в аудите; отказ и восстановление SMTP и webhook-приёмника не теряют и не дублируют уведомления; запрещённый адрес webhook отклоняется.
- **Дополнение к DoD (ADR-042):** смена дежурного меняет получателя новых эскалаций; SLA не сбрасывается, отсутствие дежурного проверено.
- **Зависимости:** 6.1.

### Шаг 6.4 Audit Service

Реализация: [ADR-021](adr/0021-audit-hash-chain.md), [руководство](engineering/audit-service.md).

  - Экспорт в CSV.

## 12. Ф7. API, read-модели, контроль доступа

### Шаг 7.1 API Gateway

Реализация: [ADR-058](adr/0058-api-gateway-and-configuration.md), [настройка, совместимость и проверки](engineering/api-gateway.md).

- **Цель:** единая защищённая точка входа.
- **Вход:** 0.5, 2.6.
- **Работы:**
  - REST v1 по контракту.
  - Проверка токенов, авторизация, ограничение частоты.
  - Ключи идемпотентности, ETag, единые ошибки.
  - CORS и заголовки безопасности.
  - Маршрутизация к сервисам: каталог, правила, инциденты, команды, сценарии, история, отчёты, аудит; единая внешняя точка вместо прямого доступа к REST сервисов.
  - Потоковая передача поэтажных планов до 20 МБ без буферизации целиком, ограничение размера тела, `Content-Type` из метаданных каталога, `X-Content-Type-Options: nosniff` и `Content-Disposition` для скачивания.
  - Снимки состояния устройств, зон и коннекторов с качеством и временем подтверждения; API обслуживания, передачи ответственности и назначения дежурного.
  - API управления отображениями нормализации и настройками retention с версиями, аудитом и публикацией в `psim.config.v1`; заменяет публикацию доверенным административным инструментом (ограничение ADR-052). Сервис-владелец API фиксируется в ADR шага.
  - Отказы в доступе публикуются в аудит.
- **Результат:** сервис API Gateway.
- **DoD:** контрактные тесты подтверждают соответствие OpenAPI; запросы без валидного токена или прав отклоняются с корректными кодами; загрузка и скачивание плана 20 МБ укладываются в настроенный предел памяти процесса.
- **Дополнение к DoD (ADR-042):** новые операции проходят матрицу прав и совместимость со старым клиентом; в снимке есть согласованный resume token.
- **Зависимости:** 3.1, 5.3.

### Шаг 7.2 Realtime-канал

- **Цель:** доставка изменений в консоль с минимальной задержкой.
- **Вход:** 0.5, 7.1.
- **Работы:**
  - WebSocket с подписками и фильтрами по области доступа.
  - Токены возобновления на основе смещений: после переподключения клиент получает пропущенное.
  - Противодавление для медленных клиентов.
  - Горизонтальное масштабирование.
  - Совместимое расширение realtime для состояния устройств, зон и коннекторов; согласование поддерживаемых потоков и типов дельт.
- **Результат:** realtime-подсистема.
- **DoD:** 500 одновременных консолей; p99 доставки ≤ 200 мс; переподключение без потери изменений.
- **Дополнение к DoD (ADR-042):** после разрыва снимок и дельты дают актуальное состояние; старый клиент получает только поддерживаемые типы; p99 доставки ≤ 200 мс.
- **Зависимости:** 7.1, 7.3.

Реализация канала: [ADR-060](adr/0060-realtime-delivery.md), [realtime](engineering/realtime.md).

### Шаг 7.3 Projection Service

- **Цель:** быстрые read-модели для консоли.
- **Вход:** 5.3, 6.1.
- **Работы:**
  - Проекции: лента активных инцидентов, состояние объектов, зон и устройств, загрузка операторов.
  - Горячие данные в Redis, запросы через PostgreSQL.
  - Полное перестроение проекций проигрыванием доступной истории Kafka; сравнение с рабочим поколением и отказ переключения при недостаточном retention.
  - Раздельная проекция жизненного цикла, связи, наблюдаемого состояния и качества actual/stale/unknown; пересчёт свежести при восстановлении.
  - Проекции дежурства, активных окон обслуживания и состояния коннекторов.
  - Перенос временных PostgreSQL-проекций инцидентов и оперативного состояния API Gateway (ADR-047, ADR-058) в Projection Service; API Gateway читает read-модели и не держит собственную копию.
- **Результат:** сервис проекций.
- **DoD:** перестроение проекций из Kafka даёт результат, идентичный рабочему; задержка обновления p99 ≤ 100 мс; сквозной сценарий M1 проходит после переноса проекции.
- **Дополнение к DoD (ADR-042):** перестроение по старым событиям не создаёт ложное online или actual; актуальный снимок подтверждает состояние после переподключения.
- **Зависимости:** 5.3.

Реализация и ограничения восстановления: [ADR-059](adr/0059-console-projections.md), [модели консоли](engineering/console-projections.md).

### Шаг 7.4 Аутентификация и авторизация

- **Цель:** управляемый доступ с минимальными привилегиями.
- **Вход:** 0.6, ADR-020 и библиотека авторизации 5.3.
- **Работы:**
  - Конфигурация realm Keycloak: клиенты, роли, сервисные учётные записи, claim `psim_scopes`; при больших областях - ссылка на набор областей (ADR-020).
  - RBAC по ролям из 0.1.
  - ABAC по областям доступа: площадка, зона.
  - Перевод Resource Catalog, управления правилами, Connector Gateway и API Gateway с собственных проверок области на библиотеку 5.3; одно правило доступа - одна реализация.
  - Отзыв доступа пользователя до истечения JWT и переаутентификация WebSocket.
  - Учётные записи коннекторов.
- **Результат:** модель доступа, конфигурация Keycloak как код.
- **DoD:** матрица «роль × операция × область» покрыта автоматическими тестами, включая негативные, для всех сервисов; собственных проверок области вне библиотеки не осталось (fitness function).
- **Зависимости:** 7.1.

- **DoD:** контракты и интеграционные проверки покрывают разрешения и отказы, повторную доставку, разрыв связи, истечение lease и конфликт версии; имитатор витрины не используется как серверная реализация.

### Шаг 8.2 Оболочка приложения

- **Цель:** основа для всех модулей.

## 14. Ф9. Развёртывание и эксплуатация

### Шаг 9.1 Топологии развёртывания

- **Статус:** Принято. Измеренная производительность локального профиля принята для шага 9.1. L-06 выполнен для отдельной границы шлюз -> Kafka; совместная производительность конвейера и независимые физические домены отказа не подтверждены.
- **Реализация:** [поставка двух топологий](engineering/deployment-topologies.md), [локальный KVM-стенд](engineering/local-vm-lab.md), [PKI и учётные записи](engineering/deployment-pki.md), [ADR-077](adr/0077-seaweedfs-deployment-topology.md).
- **Цель:** одна поставка для всех масштабов.
- **Вход:** 0.3, ADR-023 (принимается в начале шага), ADR-014, ADR-015, ADR-043, ADR-046.
- **Работы:**
  - **Одна машина:** Docker Compose или systemd-юниты, Kafka с одним брокером, ClickHouse с одним узлом и одним Keeper, явное описание ограничений надёжности.
  - **Кластер на VM:** три и более узла, Kafka с репликацией ×3, PostgreSQL под Patroni + etcd с синхронной репликацией и автоматическим переключением (проверка HA, отложенная в ADR-014), Valkey с primary, двумя репликами и Sentinel (ADR-015), ClickHouse 1 шард × 2 реплики и Keeper ×3, Keycloak ×2, HAProxy ×2 с keepalived, файловое хранилище SeaweedFS (ADR-046).
  - Полное тестирование и развёртывание Kubernetes вне MVP (X15): на этом шаге проверяется совместимость образов (без root, конфигурация файлами и переменными, health, остановка по `SIGTERM`); Helm-чарт и операторы делаются.
  - Установщик генерирует конфигурацию из профиля топологии; различия топологий - только конфигурация и число экземпляров.
  - Учётные записи и права каждого сервиса: Kafka ACL и TLS по принципалам, роли PostgreSQL по схемам, пользователи ClickHouse, ACL Valkey; распределение портов без конфликтов на одной машине, S3.
  - Регламент первоначальной настройки внешней PKI и Keycloak, доверия, регистрации и продления сертификатов.
  - Эталонный кластерный стенд E-CLUSTER для шагов 9.2, 10.1 и 10.2. Инфраструктурная часть строится параллельно с Ф6-Ф7; сервисы добавляются в профили по мере готовности.
- **Результат:** артефакты развёртывания двух топологий, ADR эксплуатационной топологии SeaweedFS, эталонный кластерный стенд.
- **DoD:** установка каждой топологии по документации; сквозной тест проходит в каждой; кластерная квалификация ввода L-06 на двух экземплярах шлюза выполнена на E-CLUSTER.
- **Дополнение к DoD (ADR-042):** установка с нуля даёт доступный план этажа и подключённый коннектор без демонстрационных секретов; нет публичного доступа к bucket; при остановке одного volume-сервера, filer или S3 gateway текущие планы читаются, после восстановления загрузка новой версии проходит и реплики томов восстановлены.
- **Зависимости:** M3; полная установка - после Ф7.

- **Вход:** 9.1, 2.4.
- **Работы:**

- **Зависимости:** 9.1.

### Шаг 9.3 Резервное копирование и восстановление

- **Статус:** Принято. Объём приёмки - реализация инструментов. Независимое целевое хранилище и полное восстановление двух топологий с измерением RPO/RTO остаются эксплуатационной проверкой.
- **Реализация:** [регламент](engineering/administration-and-recovery.md), [ADR-081](adr/0081-administration-and-recovery.md).

- **Цель:** защита данных и конфигурации.
- **Вход:** 9.1.
- **Работы:**
  - PITR для PostgreSQL: базовые копии и архив WAL вне узлов кластера.
  - Резервное копирование ClickHouse (`BACKUP` во внешнее хранилище) для данных, которые нельзя восстановить из Kafka: значимые события и связи за пределами retention топиков, факты инцидентов. Целевое хранилище копий не совпадает с bucket `psim-plans` и рабочим кластером SeaweedFS.
  - Резервирование конфигурации топиков и compacted-топиков.
  - Экспорт и импорт конфигурации продукта.
  - Регламент учений по восстановлению; целевые RPO и RTO одной машины и кластера при потере данных фиксируются в регламенте и замеряются.
  - **Файлы планов:**
    - независимая копия объектов `psim-plans` вне рабочего кластера SeaweedFS (инкрементальная репликация filer или периодическое копирование в отдельное хранилище) с отдельными учётными данными только для записи копий;
    - объекты неизменяемы, поэтому согласованность обеспечивается порядком: защитный интервал очистки неподвязанных объектов (4.4) больше окна PITR плюс интервал копирования - восстановленные на любой момент окна метаданные не ссылаются на удалённый объект;
    - порядок восстановления: объекты, затем PostgreSQL на выбранный момент, затем сверка `psimctl` - каждая ссылка каталога существует, размер и SHA-256 совпадают; лишние объекты выводятся отчётом и не удаляются автоматически;
    - мониторинг возраста последней копии и её размера.
  - Резервирование Keycloak, доверия, ключей и конфигурации с защищённым хранением; процедура перевыпуска скомпрометированных ключей. Учётные данные SeaweedFS и копий входят в защищённое хранение.
  - Резервные копии шифруются; права на чтение копий отделены от рабочих учётных записей.
- **Результат:** механизмы и регламент.
- **DoD:** восстановление на чистом стенде проверено и замерено для одной машины и кластера.
- **Дополнение к DoD (ADR-042):** на чистом стенде восстановлены планы и ссылки, вход пользователей и mTLS коннектора; истёкшие или отозванные ключи не возвращают доступ; восстановление PostgreSQL на момент до очистки неподвязанных объектов не даёт битых ссылок.
- **Зависимости:** 9.1.

## 15. Ф10. Верификация

### Шаг 10.1 Производительность

- **Цель:** подтвердить SLO.
- **Вход:** M4, 0.7, 9.2.
- **Работы:**
  - Устойчивая нагрузка L-02: 50 000 событий/с в течение 10 мин от независимых клиентов SDK; по умолчанию 100 клиентов, 10 000 устройств на 10 площадках. Проверяются суммарные подтверждения и очереди каждого клиента.

  - Длительный тест LOAD-50K в течение 10 мин измеряемой нагрузки; прогрев выполняется отдельно.
  - Запросы истории и отчётов ClickHouse под полной нагрузкой записи; проверка оценки хранения (размер строки события).
  - Модель сайзинга с экстраполяцией на целевой масштаб, включая объём SeaweedFS, резервных копий и предел горизонтального масштабирования каталога из-за сериализации изменений тенанта (ADR-051).
  - Барьер регрессии производительности в CI.
- **Результат:** отчёт о производительности, модель сайзинга.
  - Средства воспроизведения, критерии отчёта и модель ёмкости: [проверка производительности](ru/engineering/performance.md).
- **Опциональные работы вне шага 10.1:**
  - Квалификация S12/C-12: обновление N -> N+1 и откат под LOAD-50K на 10 000 устройствах и 10 площадках, устранение обнаруженных задержек и ошибки подтверждения событий локальным буфером SDK на разгоне, повторные прогоны. Критерии опциональной проверки: полная сквозная сверка без потерь и дубликатов, пауза сигналов не более 5 с и p99 событие -> инцидент не более 1 с на всём протяжении.

- **Статус объёма:** Принято. Опциональные работы не выполняются в шаге 10.1, не входят в его DoD и не блокируют выпуск.

## 17. Общий Definition of Done для каждого шага

1. Код соответствует стандарту, нет предупреждений компилятора и clang-tidy.
2. Тесты написаны и проходят, включая сборки с санитайзерами; пороги покрытия соблюдены.
3. Ревью выполнено. При работе одного инженера - чек-лист самопроверки плюс автоматизированное ревью.
4. Контракты не нарушают совместимость; документация справочников обновлена автоматически.
5. Новые компоненты экспортируют метрики, трассировку и health; дашборды и алерты обновлены.
6. Бенчмарки не показывают регрессии выше порога.
7. Меры безопасности из модели угроз, относящиеся к шагу, реализованы и проверены.
8. Решения, принятые в ходе шага, оформлены как ADR.
9. Изменение разворачивается в локальном окружении и проходит сквозной тест.
10. Для эксплуатационных функций проверены инварианты [ADR-042](adr/0042-operational-capabilities.md) и новые критерии S1-S13; правила совместимости и примечания выпуска обновлены.

## 21. Что демонстрирует инженерный уровень продукта

1. **Доказуемая корректность доставки.** Exactly-once для сигналов и инцидентов подтверждается детерминированным симуляционным тестированием с внесением сбоев, а не декларацией.
2. **Сквозная наблюдаемость.** Одна трассировка проходит от датчика до действия оператора; бюджет задержек контролируется по этапам.
3. **Воспроизводимость и «машина времени».** Любая read-модель перестраивается из Kafka; новые правила проверяются на исторических данных до активации.
4. **Контракты как продукт.** Версионируемые схемы, AsyncAPI, OpenAPI, тестовый набор соответствия для коннекторов, автоматическая проверка совместимости.
5. **Производительность как требование.** SLO с автоматическими барьерами в CI, модель сайзинга, подтверждённая замерами.
6. **Неизменяемый аудит.** Цепочка хэшей с проверкой целостности штатными средствами.
7. **Эксплуатационная зрелость.** Обновления без простоя, хаос-тесты, runbook на каждый алерт, одна поставка для всех топологий.
8. **Безопасность цепочки поставки.** Воспроизводимые сборки, SBOM, подписанные артефакты, модель угроз, связанная с реализацией.
9. **Прозрачная архитектура.** arc42, C4 как код, полный реестр ADR с альтернативами.
10. **Готовность к ИИ.** Архитектурные точки расширения (потребители топиков, шаги сценариев, ассистент оператора) позволяют добавить ИИ без изменения ядра.

## 22. Вне MVP

- ИИ: автоматическая сортировка тревог, снижение ложных срабатываний и выполнение действий моделью. Ассистент для чтения разрешённых фактов с источниками входит в оперативный интерфейс (ADR-067).
- ГИС и BIM; поэтажные планы в MVP - изображения с координатами.
- Мобильное приложение для выездных групп.
- Федерация ситуационных центров и мультитенантная эксплуатация.
- Edge-узлы на объектах (в MVP буферизацию обеспечивает Connector SDK).
- Телефония, радиосвязь, массовое оповещение.
- Видеостена.
- BI-инструменты и произвольная аналитика поверх истории событий (история событий и отчёты на ClickHouse входят в MVP, ADR-028).
- Коннекторы к продуктам конкретных производителей сверх эталонных.
- Геораспределённое резервирование.
- Сертификации.
