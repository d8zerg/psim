# ADR-008. CQRS, transactional outbox и inbox

<!-- language-links -->
[English](../../adr/0008-cqrs-outbox-inbox.md) | [Русский](0008-cqrs-outbox-inbox.md)
<!-- /language-links -->

- **Статус:** Принято
- **Связанные:** ADR-006, ADR-019, [crosscutting.md](../architecture/crosscutting.md#3-транзакционные-шаблоны)

## Контекст

Сервисы с агрегатами в PostgreSQL (каталог, инциденты, сценарии, команды, уведомления, аудит) должны публиковать доменные события в Kafka атомарно с изменением агрегата и принимать сообщения из Kafka без двойного применения. Консоль требует быстрых read-моделей (лента 10 000 инцидентов, состояние объектов), которые не должны нагружать агрегаты.

## Рассмотренные варианты

### Публикация событий

| Вариант | Плюсы | Минусы |
|---|---|---|
| Публикация в Kafka после коммита БД | Просто | Потеря события при падении между коммитом и публикацией |
| CDC через Debezium | Без кода реле, по WAL | JVM и Kafka Connect - ещё одна подсистема в поставке; задержка; формат событий привязан к таблицам |
| Собственное логическое декодирование WAL | Минимальная задержка | Сложная реализация протокола репликации, слоты репликации и их эксплуатация |
| **Таблица outbox + реле (опрос, пробуждение по `LISTEN/NOTIFY`)** | Простая надёжная реализация; события - доменные, а не строки таблиц; задержка десятки мс | Нагрузка опроса (смягчается NOTIFY и пакетами) |

### Read-модели

| Вариант | Плюсы | Минусы |
|---|---|---|
| Чтение напрямую из таблиц агрегатов | Нет отдельных моделей | Тяжёлые запросы ленты конкурируют с записью; нет восстановимости из Kafka |
| **CQRS: Projection Service строит read-модели из топиков** | Независимое масштабирование чтения; перестроение проигрыванием | Согласованность в конечном счёте (компенсируется снимком со смещениями, ADR-019) |

## Решение

1. **Outbox:** таблица `psim_outbox` в схеме каждого сервиса; запись в транзакции агрегата. Реле опрашивает таблицу каждые 100 мс по умолчанию. Транзакционная advisory-блокировка выбирает одного издателя на схему; пакет выбирается по `sequence` с ограничением строк и размера. После подтверждения публикации всего пакета Kafka реле устанавливает `published_at` и фиксирует транзакцию. При ошибке записи остаются для повтора.
2. **Inbox:** таблица `psim_inbox` с ключом `(consumer, event_id)` и отпечатком содержимого в схеме сервиса. Вставка выполняется в транзакции изменения агрегата. Повтор с тем же содержимым пропускается, другое содержимое с прежним идентификатором отклоняется. Строки inbox/outbox автоматически не удаляются; политика retention должна учитывать максимальное окно повторной доставки.
3. **Версии агрегатов:** каждое доменное событие несёт `version`; потребители проекций применяют событие, только если версия больше применённой.
4. **CQRS:** команды - к сервису-владельцу агрегата; запросы консоли - к Projection Service (лента, состояние объектов, отчётные агрегаты) или к сервисам для карточек отдельных агрегатов. Проекции перестраиваются проигрыванием топиков (`psimctl projection console rebuild`).
5. Библиотека `libs/platform/pg` реализует outbox, реле и inbox один раз для всех сервисов.

## Последствия

- Повторная публикация из outbox возможна: все потребители обязаны быть идемпотентными (ADR-006).
- Retention топиков-источников ограничивает перестроение «с нуля». Неполная история отклоняется, рабочая проекция сохраняется. Полная потеря PostgreSQL требует достаточной истории Kafka либо независимой резервной копии; детали - [проекции консоли](../engineering/console-projections.md).

## Проверка

Тест библиотеки outbox с падениями процесса в каждой точке (до коммита, после коммита, после публикации, до фиксации published_at); тест «перестроенная проекция идентична рабочей» (QS-A6).
