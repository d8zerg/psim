# ADR-006. Семантика доставки по потокам

<!-- language-links -->
[English](../../adr/0006-delivery-semantics.md) | [Русский](0006-delivery-semantics.md)
<!-- /language-links -->

- **Статус:** Принято
- **Связанные:** ADR-002, ADR-005, ADR-007, ADR-008, [data-flows.md](../architecture/data-flows.md)

## Контекст

Цели: 0 потерь событий и инцидентов, 0 дубликатов инцидентов при любых сбоях и повторах (S5, S11, QG1), при этом задержка событие -> сигнал p99 ≤ 300 мс. Каждое звено конвейера должно иметь явную семантику и механизм идемпотентности.

## Рассмотренные варианты

### Для нормализации

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. At-least-once, идемпотентность по `event_id` у потребителей | Минимальная задержка этапа | Дубликаты после падения Normalizer доходят до корреляции и искажают пороговые правила; дедупликация в Correlation Engine требует множества `event_id` с горизонтом в минуты: десятки миллионов идентификаторов при 50 000 событий/с |
| **B. Exactly-once транзакциями Kafka; трекер порядковых номеров источников в compacted-топике в той же транзакции** | Нормализованный поток без дубликатов; дедупликация в одном месте с малым состоянием (на источник - максимум и битовая карта) | Накладные расходы транзакций (интервал коммита) входят в бюджет этапа 30 мс |

### Для границы с PostgreSQL

| Вариант | Плюсы | Минусы |
|---|---|---|
| Распределённая транзакция Kafka + PostgreSQL (2PC) | Атомарность | Kafka не участвует в XA; сложность и хрупкость |
| **Inbox + outbox** | Атомарность внутри транзакции БД; стандартный шаблон | Outbox может опубликовать повторно - потребители идемпотентны |

## Решение

Классы семантики:

| Класс | Механизм | Потоки |
|---|---|---|
| **EOS-K** | Транзакция Kafka «чтение - обработка - запись»: выход, changelog и смещения входа атомарно; `transactional.id` уникален для рабочего обработчика; KIP-447 связывает фиксацию смещений с поколением группы; потребители `read_committed` | `psim.events.normalized.v1` (Normalizer), `psim.signals.v1`, `psim.correlation.*` (Correlation Engine) |
| **EOS-DB** | Inbox в транзакции изменения агрегата; смещение фиксируется после коммита БД | Вход Incident Service, Response Engine, Command Service, Audit Service |
| **Outbox** | Событие в транзакции агрегата, публикация реле; повторы возможны, потребители применяют по `version` или inbox | Все доменные события сервисов с PostgreSQL |
| **ALO+ID** | At-least-once, идемпотентность по идентификатору | Ввод от коннекторов (дедупликация в Normalizer), команды (SDK по `command_id`), результаты команд, аудит (`source_event_id`), проекции (по `version`) |

Конкретные решения:

1. Normalizer - EOS-K (вариант B); восстановление, фиксация курсоров и смена владельца партиции уточнены в [ADR-052](0052-normalization-and-event-history.md). Запасной вариант на случай превышения бюджета этапа по сквозному замеру: A с дедупликацией в Correlation Engine по `event_id` с горизонтом, равным интервалу фиксации смещений Normalizer, умноженному на запас.
2. Подтверждение коннектору - только после `acks=all` записи в Kafka.
3. Жизненный цикл команд и уведомлений публикуется в `psim.response.events.v1` (ключ - инцидент), а не в отдельных топиках: консоль и проекции получают единый упорядоченный поток по инциденту.
4. Временные ошибки (недоступность хранилища) - пауза партиции и повтор с экспоненциальной задержкой; DLQ - только для постоянных ошибок сообщения.
5. Интервал коммита транзакций - до 50 мс в Correlation Engine и до 20 мс в Normalizer; уточняется замерами.

## Последствия

- Корректность каждого звена доказывается симуляцией с внесением сбоев: падения в любой точке, повторы, переупорядочивание.
- Задержка этапов с EOS-K включает интервал коммита; бюджет [quality.md](../architecture/quality.md#4-бюджет-задержек) это учитывает.
- Все потребители outbox-топиков обязаны быть идемпотентными; библиотека платформы предоставляет inbox и фильтр по версии.

## Проверка

Сквозная сверка `source_seq` и числа инцидентов в нагрузочных и хаос-тестах; 10 000 прогонов симуляции в ночной сборке.
