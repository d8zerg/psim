# ADR-048. Connector SDK, дисковый буфер и сверка состояния

<!-- language-links -->
[English](../../adr/0048-connector-sdk.md) | [Русский](0048-connector-sdk.md)
<!-- /language-links -->

- **Статус:** Принято
- **Связанные:** ADR-004, ADR-005, ADR-006, ADR-017, ADR-042, ADR-043, ADR-047

## Контекст

Исходный минимальный симулятор реализует одну сессию непосредственно через gRPC. Интегратору нужны повторное подключение, сохранение событий при обрыве, управление потоком и безопасный приём команд. При восстановлении связи старая история не должна обозначаться как актуальное состояние оборудования.

## Решение

1. Разместить C++ SDK в `libs/platform/connector`, публичный интерфейс - `psim/platform/connector/client.hpp`, CMake-цель - `psim::platform_connector`. SDK зависит от контрактов и библиотек безопасности, не зависит от Kafka, PostgreSQL, сервисов и `platform_stream`. Один `GrpcProcess` в `main` инициализирует OpenSSL до gRPC, владеет EventEngine и завершает его после RPC-объектов. SDK использует ту же политику `OPENSSL_INIT_NO_ATEXIT`, что и gRPC: глобальный криптоконтекст имеет время жизни процесса, его нельзя выгружать одновременно с TLS-деструкторами отсоединённых потоков gRPC. RPC, каналы, сертификаты и транспортные ресурсы освобождаются при закрытии; прежнее имя в `platform_stream` сохраняется как псевдоним.
2. Использовать TLS 1.3 с обязательным клиентским сертификатом, проверкой доверия и имени сервера. Ключ читается через `security::read_secret`; публичный API не предоставляет plaintext, подмену имени или отключение проверки сертификата. Настройки и ошибки не раскрывают секреты.
3. До отправки синхронно сохранять событие в журнале. SDK присваивает UUIDv7, эпоху и монотонный номер источника. При досылке идентификатор, эпоха, номер, время и полезная нагрузка сохраняются. Подтверждение принимается только для текущего пакета с полным, непротиворечивым учётом принятых и окончательно отклонённых событий. До сохранения подтверждения событие остаётся в буфере.
4. Журнал содержит записи JSON с SHA-256 и завершающим переводом строки. Запись и подтверждение проходят `fsync`. Восстановление удаляет только незавершённый хвост; повреждение законченной записи останавливает открытие. Сжатие журнала использует отдельный файл, `fsync`, атомарное переименование и `fsync` каталога. При создании каталога синхронизируются также записи его родителей. Отдельный `flock` запрещает два владельца каталога. Каталог имеет права `0700`, файлы - `0600`; конечные символьные ссылки не принимаются. Гарантии предполагают локальную файловую систему с корректными `fsync` и атомарным `rename`, а не сетевой диск.
5. Ограничить размер журнала, число событий и реестр команд. Переполнение возвращает ошибку для противодавления источнику, старые события не вытесняются. Сжатие может временно потребовать второй файл размером до лимита журнала. После ошибки записи или синхронизации журнал требует повторного открытия; подтверждать приём внешнему источнику можно только после успешного `publish`. При неопределённом результате локального ввода-вывода оператор проверяет журнал до повторного ввода.
6. Сессия использует отдельные потоки чтения и записи gRPC; очередь входящих сообщений, очередь управления и очередь обработчиков ограничены. Есть независимый таймер регистрации/сессии, таймаут `BatchAck`, heartbeat, отмена при остановке и экспоненциальная задержка повторного подключения с разбросом. Одновременно отправлен один неподтверждённый пакет; размер ограничен параметрами шлюза, кредитами и локальным пределом 32 события / 64 КиБ.
7. Для команды сохранять запись о начале до исполнения и результате до отправки `CommandResult`. Повтор с тем же идентификатором возвращает результат, другой payload с тем же идентификатором отклоняется. Если процесс завершился между началом и сохранением результата, SDK возвращает неопределённый исход и не исполняет команду повторно. Истёкшая команда не исполняется. Журнал команд автоматически не очищается: заполнение блокирует новые команды. Физическое exactly-once действие не обещается; неизвестный результат требует проверки оборудования. Обработчик обязан учитывать дедлайн и сигнал остановки.
8. Совместимо расширить v1 полями возможностей `Register`/`Registered`, метаданными наблюдения события и сообщением `StateReport`. SDK предлагает `1.1`, затем `1.0`; новые сообщения отправляются только при согласовании `state.v1`. Возможность опросить снимок объявляется отдельно через `snapshot.v1`, только при наличии обработчика. Команды объявляются через `commands.v1`. Шлюз 1.0 продолжает принимать события; отсутствие новых возможностей не обозначает наличие сверки.
9. Сохранять границу `(source_ref, source_epoch, source_seq)` перед запросом снимка оборудования. SDK присваивает снимку именно эту границу, даже если во время запроса пришли новые события. Ввод истории по умолчанию не является текущим наблюдением; интегратор явно указывает `Observation::kCurrent` для нового наблюдения оборудования. В новой сессии все старые события отправляются с `live_observation=false`; они пополняют историю. `StateTracker` проверяет порядок, принадлежность живого события текущей сессии и качество; более старый снимок не заменяет новое состояние. Неопрошенные источники остаются `unknown`, доступность устройства передаётся отдельно от связи коннектора. Повторное подключение запускает новый запрос снимка, а не воспроизведение прежнего.
10. Предоставить диагностику и текстовые метрики Prometheus, пример коннектора и самостоятельный TLS-сервер соответствия. Набор запускает внешний исполняемый файл по документированному fixture-контракту; Kafka и прикладные сервисы ему не нужны. Обычный запуск включает реальный обрыв на 600 секунд; короткий режим служит только для отладки.

## Границы

Connector SDK реализует клиентскую библиотеку и расширение протокола. Постоянный реестр коннекторов, сессии в Redis, серверный контроль heartbeat, отзыв, квоты и маршрутизация команд реализованы Connector Gateway по ADR-049. Исходный лабораторный шлюз использовал протокол 1.0 и ограничения ADR-047, включая окно времени события; ADR-049 заменяет эти ограничения полноценной серверной обработкой. Обработка снимков и метаданных актуальности сервером, Normalizer и проекциями определена ADR-049, ADR-052 и ADR-059. Прикладные преобразования наблюдений и политика свежести задаются типом источника.

## Проверка

Модульные проверки журнала и модели состояния; настоящие gRPC/mTLS-сессии с нулевыми кредитами, потерянным подтверждением, недействительным `BatchAck`, окончательным отказом, повторной командой, истёкшим дедлайном, обновлением конфигурации, таймаутом, чужим CA и событием во время запроса снимка. Отдельный прогон выдерживает десятиминутный обрыв и перезапуск клиента с досылкой сохранённых идентификаторов без потерь. Команды запуска и fixture-контракт - в [руководстве SDK](../engineering/connector-sdk.md).
