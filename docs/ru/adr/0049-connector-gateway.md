# ADR-049. Connector Gateway: регистрации, сессии и подтверждение отзыва

<!-- language-links -->
[English](../../adr/0049-connector-gateway.md) | [Русский](0049-connector-gateway.md)
<!-- /language-links -->

- **Статус:** Принято
- **Связанные:** ADR-006, ADR-008, ADR-015, ADR-017, ADR-018, ADR-042, ADR-043, ADR-048

## Контекст

Исходный лабораторный шлюз принимает один тестовый коннектор. Для нескольких экземпляров нужны постоянные регистрации, однозначное владение сессией, серверный контроль heartbeat, доставка команд и отзыв без сохранения доступа через открытый поток. Resource Catalog вводится отдельно; регистрация доверия не должна зависеть от временной конфигурации стенда.

## Решение

1. Шлюз хранит регистрации, версии и отозванные отпечатки в схеме `ingest` PostgreSQL. Доступ разрешён только активной регистрации своего тенанта: URI SAN `psim://connector/<connector_id>`, отпечаток SHA-256 и срок сертификата должны совпадать. Публичные сертификаты проверяются по настроенному доверенному bundle; закрытые ключи не передаются. Для ротации одновременно допускаются два неистёкших сертификата. Отозванный отпечаток не добавляется снова.
2. Служба `ConnectorAdministrationService` использует тот же mTLS-listener, но принимает только URI `psim://service/gateway-admin` и проверенный JWT с ролью `admin` или `integrator`. Тенант берётся из JWT. Восстановление требует `admin`; политика MFA администратора обеспечивается IdP. Операция проверяет `expected_version`; запись регистрации, результата идемпотентного запроса и audit-outbox выполняется одной транзакцией. Повтор с тем же оператором, тенантом и `request_id` возвращает сохранённый результат; другой payload отклоняется.
3. Глобальная ревизия регистрации применяется каждым шлюзом. Кэш доверия действителен не больше секунды по монотонным часам. Обновление закрывает неподходящие потоки; шлюз подтверждает ревизию после удаления этих транспортов. Ответ управления ждёт подтверждения всех живых экземпляров. Если шлюз перестал обновлять свой трёхсекундный lease, он уже обязан прекратить работу с истёкшим кэшем. Дедлайн управления не отменяет зафиксированную транзакцию: клиент повторяет исходный запрос с тем же идентификатором.
4. Канонический lease сессии хранится в PostgreSQL. Захват сериализуется блокировкой регистрации и не заменяет живого владельца; сертификат повторно проверяется в той же транзакции. Продление не воскрешает истёкший lease. Redis содержит дополнительный TTL lease `(tenant_id, connector_id)` со случайным токеном сессии и идентификатором запуска шлюза. Захват использует `NX`; продление и удаление сравнивают прежний токен. Новый экземпляр не вытесняет действующий lease. После аварии подключение может ждать до 15 секунд. Шлюз прекращает работу до консервативно рассчитанного локального срока lease; неоднозначный результат продления закрывает поток. Потеря записи Redis не создаёт второго владельца: PostgreSQL отклоняет конкурирующий захват. Недоступность Redis блокирует приём и не отменяет долговечность клиентского журнала.
5. Согласуются протоколы `1.1` и `1.0`, возможности состояния, снимка и команд. Пакет ограничен 1000 событиями, 1 МиБ, настройками регистрации и выданными кредитами. Redis атомарно ограничивает число событий за секунду. Все записи пакета отправляются параллельно, но `BatchAck` выдаётся только после индивидуального подтверждения каждой принятой записи Kafka с `acks=all`. Окончательные ошибки отдельных событий перечисляются в ответе. Неопределённая доставка не подтверждается; повтор сохраняет идентичность события.
6. Heartbeat ожидается каждые 5 секунд; отсутствие трёх интервалов закрывает поток. Независимый таймер не блокируется ожиданием Kafka. Обновление TTL учитывает время последнего клиентского heartbeat. Статус соединения и истечение сессии фиксируются в PostgreSQL с outbox; другой шлюз публикует `offline` для истёкших сессий после аварии владельца.
7. Топик `psim.ingest.state.v1` содержит аутентифицированные изменения связи и отчёты оборудования. Новая сессия означает `unknown` для качества оборудования. Снимок согласуется отдельно; старый курсор внутри сессии не заменяет новое наблюдение. Сырые события сохраняют аутентифицированную сессию приёма и метаданные текущего наблюдения. История, чужая сессия и старое время не создают актуальность. Прикладная нормализация описана в ADR-052, REST/WebSocket-проекции состояния - в ADR-059 и ADR-060.
8. Команды читаются по ADR-018: отдельная эфемерная группа на запуск шлюза, все партиции, начало с конца. Назначение получено до открытия listener. Шлюз проверяет тенант, коннектор, канонический lease PostgreSQL, возможность исполнения и дедлайн, доставляет только своей живой сессии и принимает ответы только для ранее доставленных ей команд. Реестр незавершённых команд ограничен; неизвестный исход обрабатывается Command Service. Журнал SDK исключает повторное исполнение в пределах его гарантии долговечности.
9. Транспорт использует gRPC callback API; всё изменяемое состояние сессии обрабатывается на одном Asio-шарде. Чтение, запись и ожидание Kafka независимы. Очередь исходящих сообщений ограничена. `OnDone` освобождает reactor после завершения транспортных реакций; разделяемое состояние сохраняется до завершения асинхронного освобождения lease. Остановка дренирует операции до уничтожения клиентов инфраструктуры.

## Последствия

- Регистрация доверия доступна до появления Resource Catalog через отдельный CLI; перенос бизнес-управления в каталог не меняет протокол сессии.
- Доставка сырых событий остаётся ALO+ID. Авария между Kafka и ответом клиенту допускает повтор; дедупликация потребителей обязательна.
- Реестр в Redis - восстановимая подсказка для Command Service; владение и сроки дополнительно проверяются локально перед доставкой.
- Реестры запросов управления и отозванных сертификатов требуют резервного копирования вместе с PostgreSQL. Их очистка не должна разрешать повторное использование отозванных идентичностей.
- Данные состояния соединения не доказывают наличие свежего состояния устройства. Потребители учитывают сессию, курсор источника и время наблюдения.

## Проверка

Модульные проверки границ протокола и доверия; компонентные проверки с настоящими mTLS, Kafka, PostgreSQL, Redis и IdP; ротация и отзыв через другой экземпляр; heartbeat без клиентских ответов; история и снимок после нового события; SIGKILL шлюза с автоматическим восстановлением SDK и сверкой идентификаторов; замер двух экземпляров с подтверждёнными Kafka записями.
