## Сборка и подключения

```bash
task cpp:build PRESET=release
```

Программы: `build/debian13/release/connectors/simulator/psim-simulator`, `build/debian13/release/connectors/webhook/psim-webhook`. Пакеты: `psim-simulator`, `psim-webhook`. Команды выполняются в проектном toolchain либо после установки Debian-пакета.

Обе программы читают:

| Переменная | Назначение |
|---|---|
| `PSIM_CONNECTOR_ENDPOINT` | gRPC endpoint зарегистрированного шлюза |
| `PSIM_CONNECTOR_CA_FILE` | CA шлюза |
| `PSIM_CONNECTOR_CERTIFICATE_FILE` | Зарегистрированный сертификат клиента |
| `PSIM_CONNECTOR_PRIVATE_KEY_FILE` | Защищённый файл приватного ключа |
| `PSIM_CONNECTOR_BUFFER_DIRECTORY` | Постоянный отдельный каталог SDK |
| `PSIM_CONNECTOR_FLUSH_TIMEOUT_SECONDS` | Время ожидания отправки симулятора, по умолчанию 120 секунд |

Сертификат нужно зарегистрировать административным CLI шлюза. Каталог сохраняется при перезапуске, имеет одного владельца и не разделяется между программами. Отправка при потере связи возобновляется автоматически; исчерпание квоты останавливает приём.

## Симулятор

```bash
psim-simulator --buffer /var/lib/psim-simulator --devices 10000 \
  --count 500000 --scenario mixed --run-id test-1
psim-simulator --buffer /var/lib/psim-simulator --devices 5000 \
  --count 100000 --rate 10000 --scenario burst --burst-every 10000 --burst-size 1000
```

`--scenario`: `alarm` -> ALARM, `fire` -> FIRE, `offline` -> OFFLINE, `mixed` -> чередование трёх кодов. В `burst` первые `burst-size` событий каждого периода назначены на один момент; остальное расписание сохраняет среднюю скорость `--rate`. Код в `burst` - ALARM. `--manifest <path>` сохраняет UUID принятых в журнал событий по одному на строку для последующей сверки. `--source-prefix` задаёт префикс источников, по умолчанию `device-`.

Пределы: 100 000 устройств, 100 млн событий, 1000 событий в локальном пакете. `--batch` по умолчанию 500. При ненулевом `--rate` события вводятся по одному согласно открытому расписанию. При `--rate 0` генерация не ограничена расписанием и используется пакетная запись SDK. Буфер симулятора ограничен 512 МиБ и 1 млн неподтверждённых событий.

Событие несёт `generator_run` и глобальный `generator_seq`; SDK отдельно присваивает UUIDv7, эпоху и номер каждого источника. Итоговая строка JSON содержит скорость долговечной генерации, время доставки, подтверждения, отказы, остаток и максимальное опоздание расписания. Постоянный отказ выводится в stderr и даёт ненулевой код выхода.

Команды `arm` и `disarm` адресуются `device-N`, без параметров. Проверяются устройство, возможность, остановка и дедлайн. Снимок содержит доступность и значение `armed` для первых 1000 источников, в пределах SDK; остальные остаются unknown. В сценарии `offline` снимок показывает offline. Состояние виртуального оборудования хранится в памяти; журнал команд SDK переживает перезапуск и предотвращает повторное исполнение.

Прямой клиент проверки M1 находится в `tools/event-flow/psim-flow-simulator`. Он используется Compose для намеренных повторов и замеров трассировки. Модельный стенд `libs/sim` запускается отдельно.

## Webhook/HTTP

Кроме настроек SDK нужны:

| Переменная | Назначение |
|---|---|
| `PSIM_WEBHOOK_TOKEN_FILE` | Файл Bearer-токена, 32-256 байт без пробелов и перевода строки, права 0400/0600 |
| `PSIM_WEBHOOK_CERTIFICATE_FILE` | Серверный сертификат HTTPS |
| `PSIM_WEBHOOK_PRIVATE_KEY_FILE` | Защищённый приватный ключ HTTPS |
| `PSIM_WEBHOOK_ADDRESS` | Адрес прослушивания, по умолчанию 127.0.0.1 |
| `PSIM_WEBHOOK_PORT` | Порт, по умолчанию 8443 |

```bash
psim-webhook
```

`POST /v1/events`, `Content-Type: application/json`, `Authorization: Bearer <token>`, `Idempotency-Key: <key>`. Формат:

```json
{
  "source_ref": "door-1",
  "raw_code": "ALARM",
  "occurred_at": "<RFC3339 timestamp>",
  "attributes": {"upstream": "alarm-123"}
}
```

Первые три поля обязательны; `attributes` - необязательный объект строк. Неизвестные и повторяющиеся поля отклоняются. `source_ref` - до 256 байт, `raw_code` - до 128, до 64 атрибутов с ключами до 256 и значениями до 4096 байт. Тело ограничено 64 КиБ, сериализованное событие - 64 000 байт. Время источника обязательно, история не получает признак текущего наблюдения. UUID и последовательности HTTP-клиент не задаёт.

Ключ содержит 1-128 ASCII-букв, цифр либо `-_.:`. Он уникален в пределах постоянного каталога коннектора. Возвращается 202 и квитанция `{event_id, source_epoch, source_seq, status: "buffered"}` после `fsync`; при недоступном шлюзе событие остаётся в журнале. Это ещё не подтверждение Kafka.

| Ответ | Действие отправителя |
|---|---|
| 202 | Сохранить квитанцию; повтор с тем же ключом и содержимым вернёт её снова |
| 400 / 415 | Исправить формат; данные не приняты |
| 401 | Исправить аутентификацию |
| 409 | Ключ уже использован с другим содержимым; проверить источник |
| 503 / потеря ответа | Повторить с прежним ключом и содержимым, с экспоненциальной задержкой и jitter |

Изменение порядка JSON-полей не меняет содержимое. Реестр ключей сохраняется после подтверждения шлюза, сжатия и перезапуска; по умолчанию ограничен 100 000 ключей и общей квотой SDK 64 МиБ. Старые ключи не вытесняются. При заполнении новые ключи получают 503; существующие повторы продолжают возвращать квитанции. Нужен контроль квот и плановая смена экземпляра и пространства ключей. Удаление рабочего каталога нарушает гарантии.

HTTP сам по себе не подтверждает возможность опросить устройство или выполнить команду. Webhook не объявляет `commands.v1` и `snapshot.v1`; качество устройства остаётся unknown до отдельного подтверждённого наблюдения.

`GET /healthz` показывает подключение и глубину буфера; `GET /metrics` - метрики SDK. Оба endpoint требуют тот же Bearer-токен. SIGTERM прекращает приём, ждёт отправку до 5 секунд и сохраняет остаток. Окончательные отказы шлюза пишутся в stderr с идентификатором и кодом; отправитель должен сверять их с квитанциями.

Пример отправителя: [send_webhook.py](../../../tools/connectors/send_webhook.py). Он читает JSON из файла, токен из защищённого файла, проверяет CA и повторяет только сетевые ошибки и 503 с тем же ключом.

## Проверка

```bash
task connectors:conformance                    # SDK example and both connectors, 600-second outages
task connectors:conformance OUTAGE_SECONDS=1   # Short diagnostic run
task connectors:bench                          # Release build, 75,000 events/s generation gate
task connectors:coverage
task connectors:sanitizers
# With the local environment running:
task connectors:integration
```

HTTP-fixture использует настоящий HTTPS-сервер, проверяет аутентификацию, валидацию, повторы, конфликт ключа, восстановление и постоянный отказ. Симулятор проверяет также команды и свежий снимок. Артефакты соответствия: `build/connector-conformance/<preset>/{example,simulator,webhook}`.

Перед замером генератора завершите другие сборки и нагрузочные проверки на той же машине.

Нагрузочный приёмник проверяет mTLS, кредиты, пакеты, полный набор `generator_seq` и порядок каждого источника. Отчёт `build/reference-connectors/release/load/result.json` отдельно показывает скорость генерации и время доставки. Этот замер проверяет генератор и транспортный протокол, не пропускную способность Kafka или всей платформы.
