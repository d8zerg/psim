# Локальный стенд на VM

<!-- language-links -->
[English](../../engineering/local-vm-lab.md) | [Русский](local-vm-lab.md)
<!-- /language-links -->

Статус: Принято. Стенд используется для разработки кластерной поставки. Одна физическая машина не воспроизводит независимые физические домены отказа и не заменяет эталонный кластер для подтверждения производительности.

## Ресурсы

Профиль [local.json](../../../deploy/vm/local.json) создаёт три VM Debian 13 x86_64. Для node-1/node-2/node-3 выделены 6/6/4 vCPU. На каждую VM выделены 12288 МиБ RAM и 60 ГиБ диска. Всего требуется 16 vCPU, 36 ГиБ RAM и 180 ГиБ логического дискового пространства. Диски copy-on-write используют общий базовый образ; первоначальный физический объём существенно меньше логического.

Проверенный хост: AMD Ryzen 9 3900X, 24 логических CPU, 64 ГБ RAM, NVMe. Проверка перед запуском требует дополнительно 8 ГиБ доступной памяти и 20 ГиБ свободного диска для хоста. Учитываются резервирования других работающих управляемых стендов. KVM обязателен; программная эмуляция не используется.

## Изолированный нагрузочный стенд

[Профиль VM isolated](../../../deploy/vm/isolated.json) и [инвентарь развёртывания](../../../deploy/topologies/local-isolated.json) разделяют приложения, Kafka и БД. Статус: Принято для диагностических нагрузочных тестов. Kafka использует один брокер, фактор репликации 1 и minimum ISR 1; этот профиль не квалифицирует реплицированный кластер.

| VM | Размещение | vCPU | RAM | Логический диск |
| --- | --- | ---: | ---: | ---: |
| node-1 | Продуктовые сервисы, edge, Keycloak, Schema Registry | 4 | 9 ГиБ | 45 ГиБ |
| node-2 | Продуктовые сервисы, edge, центральный мониторинг | 4 | 9 ГиБ | 45 ГиБ |
| node-3 | Kafka | 4 | 9 ГиБ | 45 ГиБ |
| node-4 | PostgreSQL, ClickHouse, Valkey, Keeper, объектное хранилище | 4 | 9 ГиБ | 45 ГиБ |

На каждой VM также работают агенты мониторинга и телеметрии. Суммарно сохранены 16 vCPU, 36 ГиБ RAM и 180 ГиБ логического диска. Число партиций топиков соответствует кластерному профилю, чтобы изменение репликации не уменьшало параллелизм потребителей. Профили `single` и `cluster` сохраняют прежние параметры репликации.

```sh
task deploy:isolated:up
task deploy:isolated:status
task deploy:isolated:down
```

Пространство имён - `PSIM_LAB_ID=isolated`. Явный `VERSION` позволяет выбрать уже собранные образы выпуска при создании стенда. Перед публикацией тех же портов хоста прежний трёхузловой стенд останавливается; его диски, защищённые материалы и запись фабрики сохраняются в прежнем пространстве имён. Изолированный стенд создаёт отдельную установку и не переносит существующие данные. Оба варианта по-прежнему используют общие физические CPU и SSD; результаты RF=1 учитываются отдельно от квалификации RF=3.

## Управление

Команды выполняются из корня репозитория на Linux с нативным Docker Engine и доступными `/dev/kvm` и `/dev/net/tun`.

```sh
task vm:doctor
task vm:up
task vm:status
task vm:exec NODE=node-1 CMD='uname -r'
task vm:bootstrap
task vm:down
task vm:up
task vm:destroy
```

`up` создаёт VM или возобновляет их, проверяет завершение cloud-init и сбрасывает первоначальные записи на диски. Повторный `up` сохраняет работающие VM. `bootstrap` устанавливает закреплённые по версиям и SHA-256 пакеты Docker Engine и Compose внутри гостевых ОС. Установка сервисов платформы выполняется отдельно.

`down` завершает гостевые ОС и сохраняет диски, SSH-ключи и идентификаторы. `destroy` удаляет контейнер управления и каталог только указанного управляемого стенда. Общий кеш базового образа и пакетов сохраняется. После изменения только числа CPU в профиле `task vm:resize-cpu` завершает и запускает VM с прежними дисками, SSH-идентификаторами и данными установки. Команда отклоняет остальные изменения профиля и восстанавливает прежнюю конфигурацию CPU при сбое запуска. Смена памяти, дисков, адресов или bootstrap требует явного пересоздания стенда. Публикацию портов можно изменить через `down/up` с сохранением гостевых дисков.

```sh
task vm:node:kill NODE=node-1
task vm:node:start NODE=node-1
task vm:wait
```

`node:kill` имитирует потерю питания выбранной VM. Сохраняются только данные, сброшенные гостевой ОС на диск. Другие узлы продолжают работать.

## Сеть и доступ

VM соединены мостом в сетевом пространстве контейнера управления: `10.91.0.11`, `10.91.0.12`, `10.91.0.13`, шлюз и DNS `10.91.0.1`. SSH опубликован только на `127.0.0.1:2211`, `:2212`, `:2213`. Проверка ключа сервера обязательна; ожидаемые ключи задаются до первого подключения. Парольный вход и вход root запрещены. Пользователь `psim` выполняет административные команды через sudo внутри своих VM.

QEMU и SSH-инструменты работают из контейнера. QEMU использует UID пользователя хоста. Контейнер получает KVM, TUN и необходимые права для собственной сети и управления дочерними процессами; сеть хоста и сокет Docker внутрь него не передаются.

Состояние находится в `.cache/vm/psim-platform-vm`, каталог имеет режим `0700`. Закрытые ключи и NoCloud-носители не добавляются в Git и не включаются в диагностические отчёты. Не выводить содержимое `user-data` и закрытых ключей: NoCloud содержит ключ сервера SSH.

## Проверка

```sh
task vm:test
```

Проверка использует отдельное имя `psim-platform-vm-test` и SSH-порты `2311-2313`; требуется свободный ресурсный бюджет для трёх VM. Она отказывается использовать уже существующее окружение с таким именем.

Проверены десять модульных тестов границ профиля и владения: неверные ресурсы и адреса, повторяющиеся узлы, подмена каталога символьной ссылкой, чужой UID или путь состояния, чужой контейнер, повреждённая загрузка образа, отказ запроса к Docker, прерванная запись состояния, ограничения изменения CPU, повторный вызов и откат при сбое запуска.

Нативная проверка подтвердила три независимых гостевых ядра KVM, заданные CPU/RAM/диски, повторный `up` без перезагрузки, TCP между узлами, публикацию порта на localhost, аппаратный watchdog, доступность двух узлов после выключения третьего, сохранность сброшенных данных после аварийного и штатного перезапуска и удаление собственного окружения. Отчёт: `build/vm/qualification.json`. Готовность PostgreSQL, Kafka, SeaweedFS и прикладного конвейера этим тестом не подтверждается.
