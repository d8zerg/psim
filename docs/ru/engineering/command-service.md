# Сервис команд устройствам

<!-- language-links -->
[English](../../engineering/command-service.md) | [Русский](command-service.md)
<!-- /language-links -->

Command Service предоставляет HTTPS API `/v1/commands`, хранит жизненный цикл в собственной схеме PostgreSQL `command` и доставляет действия через Connector Gateway и SDK. Решение: [ADR-055](../adr/0055-command-service.md).

## Запрос и доступ

`POST /v1/commands` принимает `commandId`, `deviceId`, `capability`, `parameters` и необязательную связь с инцидентом и шагом сценария. Заголовок `Idempotency-Key` равен `commandId`. Сервер определяет критичность по типу устройства, проверяет параметры и активность устройства и коннектора. Допустимо до 64 параметров, имя до 128 байт и значение до 1024 байт. Размер сообщения запроса Protobuf ограничен 30 000 байтами, чтобы команда с полями маршрутизации помещалась в кадр SDK размером 32 КиБ. Одинаковый запрос того же инициатора возвращает актуальное состояние; другое содержимое или инициатор дают `COMMON_IDEMPOTENCY_KEY_REUSED`.

Чтение доступно operator, supervisor и auditor. Запрос и отмена доступны operator и supervisor; подтверждение и отказ - supervisor. Общая библиотека авторизации проверяет тенант и области устройства и связанного инцидента. Собственное подтверждение запрещено, включая supervisor. Отказы фиксируются в аудите.

`GET /v1/commands` поддерживает фильтры `incidentId`, `deviceId`, `states`, `pageSize` и `pageToken`. Размер страницы не больше 1000; курсор продолжает поиск по идентификаторам. Список содержит только доступные команды. Изменения `:approve`, `:reject` и `:cancel` требуют `If-Match` с версией из ETag и UUID в `Idempotency-Key`. Повтор подтверждённого запроса с тем же ключом возвращает актуальную команду, даже если версия уже изменилась.

Response Engine передаёт команды шагов через CommandRequested в `psim.response.events.v1`. Получатель проверяет сервисного отправителя и идентичность инициатора. Ручной шаг сохраняет проверенного пользователя инициатором, автоматический - Response Engine. Полученная область ограничена зоной инцидента; проверки каталога, критичности и отдельного подтверждения выполняются тем же обработчиком, что для HTTPS API. Конечный отказ при приёме запроса сохраняется как FAILED и публикуется в ответ. Повтор одного идентификатора не создаёт второго исполнения.

## Доставка и результат

- Некритичная команда отправляется сразу. Критичная остаётся в `AWAITING_APPROVAL`; перед подтверждённой отправкой повторно проверяется конфигурация устройства.
- SessionRegistry Valkey выбирает сессию. Отсутствие сессии завершает команду с `COMMAND_CONNECTOR_OFFLINE`; ошибка Valkey возвращается как ошибка инфраструктуры.
- Доставка в `psim.commands.v1` содержит `session_id`. Шлюз передаёт её только выбранной сессии. Повторная публикация outbox безопасна благодаря долговечному журналу SDK.
- `SENT` означает сохранённую доставку в outbox. Квитанция из `psim.commands.results.v1` переводит команду в `ACKNOWLEDGED`, результат - в `EXECUTED` или `FAILED`. Результат проверяется по тенанту, коннектору и сессии; inbox исключает повторный эффект.
- Потеря сессии после отправки завершает команду в `UNKNOWN` с `COMMAND_OUTCOME_UNKNOWN`. Автоматическая отправка в новую сессию запрещена. Оператор проверяет состояние оборудования перед новым действием.
- Дедлайн завершает неподтверждённую команду с `COMMAND_APPROVAL_TIMED_OUT`, отправленную - с `COMMAND_TIMED_OUT`. Поздние результаты не изменяют конечное состояние. После перезапуска проверяются сохранённые дедлайны.

Изменения команды, аудит и outbox записываются одной транзакцией. `CommandUpdated` публикуется в `psim.response.events.v1`; Incident Service добавляет каждую версию команды в хронологию, включая запоздавшие изменения, сохраняя жизненный цикл, ответственного и SLA инцидента.

## Конфигурация и эксплуатация

Используются общие параметры потокового сервиса для PostgreSQL, Kafka, Schema Registry, JWT/JWKS и TLS. Дополнительные параметры: `redis_host`, `redis_password_file`, `redis_ca_file`, `redis_certificate_file`, `redis_key_file`, `command_timeout_seconds` (по умолчанию 30, допустимо 1-240). HTTPS использует `tls_certificate_file` и `tls_private_key_file` либо `command-server.pem` и `command-server.key` в `tls_directory`.

Каталог и снимки инцидентов читаются из Kafka в собственные монотонные проекции PostgreSQL. До поступления ресурса запрос отклоняется. Для восстановления проекций нужны сохранённые записи исходных топиков. Сервис не читает таблицы других сервисов. Изменения области устройства после создания команды требуют нового запроса; старую ожидающую команду можно отменить.

Диагностика runtime: `/health/live`, `/health/ready`, `/metrics`, OTLP и JSON-логи. Метрика `psim_command_result_seconds` измеряет транзакцию обработки результата; `psim_command_results_ignored_total` считает повторные, неизвестные и уже завершённые результаты. Ошибки фоновой обработки видны в логах; сохранённые outbox и дедлайны обрабатываются повторно после восстановления зависимостей.

## Проверка

Все команды запускаются на Linux с нативным Docker Engine и Docker Compose. Проверки используют отдельный Compose-проект `psim-command-test`; имя проекта задаётся в [задачах проверки](../../../tools/taskfiles/commands.yml):

```
task commands:test
task commands:sanitizers
task commands:coverage
task commands:bench
```

Проверка запускает два Command Service, Incident Service, настоящий шлюз, SDK, Kafka, PostgreSQL, Valkey и Keycloak. Артефакты находятся в `build/commands/<preset>/`: отчёт, журналы процессов, исполнения SDK и входные наборы. Release-замер подаёт 10 команд/с согласно объёму команд MVP ([ADR-018](../adr/0018-command-routing.md)), сверяет идентификаторы всех команд и проверяет p99 от начала HTTPS-запроса до вызова обработчика SDK не больше 200 мс.
