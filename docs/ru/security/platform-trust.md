# Доверие, сертификаты и секреты платформы

Решение - [ADR-043](../adr/0043-platform-security.md), интерфейсы - [библиотека безопасности](../repository/libs/platform/security/README.md). Документ описывает правила для реализации сервисов и оператора PKI. Установка на Debian и VM описана в [топологиях](../engineering/deployment-topologies.md), административный CLI - в [эксплуатации и восстановлении](../engineering/administration-and-recovery.md). Kubernetes не входит в квалифицированные топологии; статические Helm-артефакты описаны отдельно в руководстве топологий.

## Границы и идентичность

| Соединение | Требование |
|---|---|
| Коннектор -> шлюз | TLS 1.3, mTLS, EKU clientAuth, URI SAN `psim://connector/<connector-id>`, отпечаток в каталоге |
| Браузер -> API | HTTPS TLS 1.3, access token Keycloak; сертификат браузера не требуется |
| Сервис -> сервис | mTLS, URI SAN `psim://service/<client-id>`, access token сервиса или пользователя, разрешённый список отправителей |
| Сервис -> Kafka/PostgreSQL/Valkey | Проверка CA и имени; mTLS или учётные данные сервиса по TLS; права по сервисам |
| JWKS, Schema Registry, OTLP | Настроенный защищённый endpoint, проверка CA и имени; ключи нельзя загружать по URL из токена |

Тенант определяется только аутентифицированным principal или регистрацией сертификата. Переданный клиентом tenant_id и сам URL/SAN без доверенной цепочки не дают доступа. После проверки личности сервис самостоятельно проверяет действие и область доступа.

## Внешняя PKI

Для новой установки используется внешняя step-ca и step CLI под управлением оператора. Существующий УЦ организации допустим с тем же профилем сертификатов. Платформа не хранит ключи УЦ и не подписывает сертификаты. Root CA хранится отдельно, выдаёт сертификаты intermediate CA; рабочая выдача выполняется intermediate. Для проверки отзыва каждого уровня нужен полный актуальный PEM bundle CRL.

Оператор задаёт provisioner и ограничивает допустимые URI SAN и роли. Подписанная CSR подтверждает владение ключом, но не право на произвольный connector-id, tenant или service-id. Саморегистрация по одному сертификату запрещена.

1. Сгенерировать P-256 ключ на узле владельца; установить владельца сервисного пользователя и `0400`. Создать CSR через `make_csr` с нужным URI SAN.
2. Подписать CSR через `step ca sign` либо корпоративную PKI. Не передавать пароль provisioner или одноразовый токен выдачи в открытой конфигурации платформы, журнале или диагностическом пакете.
3. Проверить подпись, цепочку, SAN, EKU и срок. Сертификат коннектора действует не более 365 суток; для автоматизированных сервисов рекомендуется короткий срок с заранее настроенным продлением.
4. Уполномоченный оператор связывает отпечаток SHA-256 и connector-id с тенантом через управление регистрациями Connector Gateway. Resource Catalog может проксировать операцию; постоянная регистрация принадлежит Connector Gateway. Сам факт доверия УЦ не заменяет эту запись.
5. Доставить CA, CRL и сертификат на узлы, а закрытый ключ оставить у владельца. Не использовать сертификаты из `.cache/` окружения разработки.

[step CLI sign](https://smallstep.com/docs/step-cli/reference/ca/sign/) и [правила эксплуатации step-ca](https://smallstep.com/docs/step-ca/certificate-authority-server-production/) описывают внешний инструмент. CRL нужно включить и обновлять отдельно; автоматическое истечение короткого сертификата не закрывает активную сессию мгновенно.

## Продление и отзыв

- Выпустить новый сертификат с новым ключом, прежними идентичностью и областью. До окончания перехода разрешены два отпечатка. Третий сертификат не добавляется.
- Проверить новый материал и опубликовать новый TLS-контекст. Ошибка чтения, несовпадение ключа и сертификата или некорректный CA оставляет прежний рабочий контекст.
- Переподключить коннектор с досылкой из SDK и прежней моделью подтверждений. Старый поток работает в пределах срока и регистрации; прикладной шлюз сохраняет кредиты, порядок и дедупликацию.
- После успешного перехода отозвать прежнюю регистрацию, закрыть её сессии на всех шлюзах, дождаться подтверждений, затем удалить прежний материал. Повторное применение отзыва идемпотентно.
- При компрометации сначала отозвать регистрацию и закрыть потоки, затем применить отзыв в PKI (`step ca revoke` или корпоративный инструмент), обновить CRL и контексты. Обновление CRL само по себе не закрывает уже открытый поток.
- Проверять срок на каждом сообщении и вызывать `ConnectorTrust::expire` по таймеру. Истёкший сертификат запрещён даже в прежнем открытом соединении.

Компонентная проверка библиотеки безопасности проводит 200 последовательных тестовых событий через два настоящих mTLS-потока: продление сохраняет старый поток, отзыв отменяет его чтение, новый поток продолжает работу. Проверка всего конвейера, распределённого отзыва и досылки SDK выполняется сетевыми проверками шлюза и TS-22.

## Восстановление доступа

Восстановление выполняет уполномоченный оператор с MFA. Новый сертификат должен быть свежим и разрешённым внешней PKI; владение новым ключом не заменяет авторизацию восстановления. Реестр закрывает все прежние сессии и заменяет разрешённые отпечатки, сохраняя запрет прежних сертификатов до их истечения. Причина, инициатор, старые и новые отпечатки фиксируются в аудите Connector Gateway. Резервное копирование должно сохранять регистрации и отзывы, чтобы восстановление старого backup не возвращало доступ скомпрометированному ключу.

## Секреты и ротация

В конфигурации - только ссылка на файл. Файл должен быть обычным, принадлежать пользователю сервиса и иметь точные права `0400`; symlink, FIFO, чужой владелец, открытые права и превышение размера отклоняются. Отказ чтения не раскрывает путь и содержимое.

Закрытые ключи не передаются в JWT, Kafka, логи, trace attributes и диагностические пакеты. `Secret` очищает свой буфер; драйверы хранят переданные учётные данные в своей памяти. Ротация файла и проверка нового снимка выполняются на управляющем или блокирующем executor, затем публикуется новое состояние. Не перезаписывать существующий рабочий ключ до проверки нового сертификата.

Для Kafka `TransportSecurity::password_file` содержит только SCRAM-пароль, без завершающего перевода строки. Для конфигурационных секретов `Config::secret` сохраняет прежнее удаление завершающих CR/LF. Права топиков, схем, таблиц и команд отдельно настраиваются для каждого сервиса в установщике.

## Отказ Keycloak и ротация JWKS

Issuer, audience, HTTPS endpoint JWKS и клиент ролей заданы оператором. Keycloak включает `psim` в audience access token консоли и сервисов. В поставке каждый сервис имеет собственный client credentials и соответствующий URI SAN; общий `psim-services` предназначен для локального окружения.

Кэш обновляется по сроку или неизвестному `kid` с ограничением частоты. Успешный ответ заменяет набор ключей, включая удаление прежних. При отказе IdP известные ключи работают до `max_stale`, но JWT всё равно проверяется по собственным `exp`, `iat` и `nbf`. Неизвестный ключ, устаревший кэш и неверная подпись запрещают доступ. Отзыв отдельного пользователя до истечения JWT, права ролей и переаутентификация WebSocket реализованы в API Gateway и сервисах-владельцах по ADR-061.

Правила кэша ключей относятся к проверке подписи. Авторизация также требует актуальной introspection: отказ Keycloak не продлевает время кэширования доступа 500 мс. Предел JWKS `max_stale` не продлевает актуальность авторизации.
