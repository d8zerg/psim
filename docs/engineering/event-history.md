# Поиск истории и связь с инцидентами

Реализация шага 5.4 расширяет существующий Event History. Решения: [ADR-054](../adr/0054-event-history-links.md), [ADR-028](../adr/0028-clickhouse-analytical-storage.md), [ADR-052](../adr/0052-normalization-and-event-history.md).

## Запуск

Сервис использует прежние настройки PostgreSQL, Kafka и ClickHouse. `history_api: true` включает HTTPS API; профиль загрузчиков без API сохраняет совместимость с прежним стендом. `listen_port` задаёт порт. `tls_certificate_file`, `tls_private_key_file`, `tls_ca_file`, `jwks_ca_file`, `issuer` и `jwks_url` задают TLS и проверку JWT. Локальный тест использует сертификат `history-server`; поставка задаёт явные файлы.

`history_batch_messages` ограничивает входной пакет (по умолчанию 5000, максимум 50 000); предел подготовленного блока остаётся 8 МиБ. `history_batch_wait_ms` ограничивает время сбора пакета (по умолчанию 100 мс, максимум 1000 мс). Нагрузочный release-профиль использует четыре экземпляра, максимум 50 000 сообщений в пакете, окно 500 мс и восемь blocking threads на экземпляр. Отказные проверки используют два экземпляра.

`history_read_user` и `history_read_password_file` позволяют выделить пользователя ClickHouse только с SELECT для чтения API. Без них используется соединение, настроенное для загрузки. Секрет хранится в файле 0400, принадлежащем пользователю процесса. Сетевые запросы Keycloak не выполняются для каждой строки: API применяет проверенную область токена через `libs/platform/authz`.

## API

- `GET /v1/events` - события за обязательный интервал `from` и `to`, новые сначала. Максимальный интервал поиска - 31 сутки. Фильтры: повторяющиеся `siteIds`, `zoneIds`, `deviceIds`, `types`, `minSeverity`, `significantOnly`. Объект задаётся площадкой `siteIds`; поиск по иерархии зданий и этажей требует предварительно выбрать зоны каталога. Тип поддерживает точное значение и префикс с окончанием `.*`.
- `GET /v1/events/{event_id}` - одно доступное событие. Необязательные `from` и `to` уточняют интервал; по умолчанию - последние 90 суток. Неизвестный или недоступный в области и интервале идентификатор возвращает 404.
- `GET /v1/incidents/{incident_id}/events` - события через все сигналы инцидента. `unavailableEventIds` содержит ссылки без доступного тела. Применяется область как инцидента, так и исходных событий; ссылка не расширяет доступ к другой зоне.
- `GET /v1/events/rule-statistics` - срабатывания по rule_id и неизменяемой rule_version за обязательный интервал до 31 суток. Дополнительные фильтры - площадки, зоны, ruleIds. `signalCount` считает логически уникальные сигналы, `eventReferenceCount` - уникальные свидетельства каждого сигнала, а не глобально уникальные события.

Размер страницы по умолчанию - 100, максимум - 1000. `nextPageToken` передаётся как `pageToken` с прежними фильтрами. Курсор не подходит для другой области или другого запроса. Поиск упорядочен по времени и ID; связи инцидента - по ID источника, статистика - по ID и версии правила. Пагинация не замораживает весь набор данных при продолжающейся записи.

Историю читают operator, supervisor и auditor. Статистику настройки правил читают supervisor, integrator, admin и auditor. Тенант и область обязательны; пустая область возвращает пустой набор. UUID, фильтры, даты и курсоры валидируются. Запросы имеют пределы размера результата и времени выполнения.

## Хранение и восстановление

`events` сохраняет полный нормализованный поток. `history_facts` содержит сигналы и данные связей событий инцидента; представления `signal_facts`, `event_signals` и `incident_signals` читают его с `FINAL`. Это аналитическая проекция, а не источник истины Incident Service. Статистика итогов инцидентов и отчёты относятся к 6.5.

Сигнал продлевает хранение своих исходных событий по значимой политике. Очередь `history.retentions` хранит запрос до подтверждённой записи `retained_events`; обратный порядок доставки не теряет запрос. Повтор вставки после SIGKILL не меняет логический результат. При чтении объединяются исходная и продлённая копии; повторные события и ссылки не появляются в API. TTL удаляет обе категории независимо. После физического удаления источника ссылка сама по себе не позволяет восстановить тело; для этого нужен доступный исходный журнал или резервная копия.

## Проверки

```sh
task history:test
task history:sanitizers
task history:coverage
task history:bench
```

Отчёты сохраняются в `build/event-history/<preset>/`, нагрузочный отчёт - в `build/event-history/release-bench/`. Функциональный стенд проверяет два процесса, обратный порядок событий и сигналов, области доступа, пагинацию, TTL, остановку ClickHouse и SIGKILL загрузчиков. Сверяются полные множества идентификаторов связей. Release-замер отдельно проверяет поиск за сутки во время записи не менее 50 000 событий/с; оценка включает TLS, проверку JWT, ClickHouse и сериализацию ответа. Нагрузочный замер запускают после завершения остальных конвейеров на хосте. Полная длительная кластерная нагрузка остаётся в проверках поставки.
