# Realtime delivery

API Gateway обслуживает `wss://<host>/v1/realtime`. Решение и совместимость описаны в [ADR-060](../adr/0060-realtime-delivery.md), исходный протокол - в [ADR-019](../adr/0019-realtime-channel.md). Снимки предоставляет [Projection Service](console-projections.md).

## Подключение и подписки

Клиент получает REST-снимок, открывает WebSocket с разрешённым Origin и отправляет Authenticate с JWT. `supported_change_types` задаёт понимаемые типы: `incident_event`, `response_event`, `location_status`. Пустой список сохраняет прежний `incident_event`. Authenticated возвращает пересечение поддерживаемых типов и доступные потоки. Общий TypeScript-клиент предоставляет `supportedChangeTypes` и обработчик `onCapabilities`.

`STREAM_INCIDENTS` передаёт события ленты, `STREAM_INCIDENT` требует `filter.incident_id`. Фильтры `site_ids` и `zone_ids` пересекаются с проверенными областями JWT; они не расширяют доступ. Тенант берётся из JWT. Закрытие инцидента доставляется как обычное изменение, чтобы клиент удалил его из активной ленты. Версии агрегатов защищают применение от повторов.

`response_event` включает изменения сценария, SLA, эскалации, политики, отсутствия плана и дежурства. Для событий без площадки Gateway проверяет инцидент через Incident Service с исходным JWT. Недоступность проверки требует нового снимка. Приватные уведомления и намерения доставки команд или уведомлений исключены. Роль дополнительно проверяется для чтения сценария или дежурства.

Соединение поддерживает независимые подписки с уникальными `subscription_id`. Unsubscribe прекращает подписку. Повторный Authenticate обновляет JWT. Смена тенанта, ролей, областей или типов очищает очередь и отменяет прежние подписки с ResyncRequired. Истёкший JWT закрывает соединение; сервер не отправляет данные после срока действия. До первой аутентификации отведено 5 секунд.

## Возобновление

Токен непрозрачен для клиента. Версия 2 содержит тенант, время выпуска и векторы следующей позиции всех партиций `psim.incidents.events.v1` и `psim.response.events.v1`. Он не зависит от узла Gateway. Клиент сохраняет токен только после успешного применения Delta и передаёт последний токен при восстановлении. TypeScript-клиент при исключении синхронного обработчика закрывает соединение и повторяет чтение с прежнего токена; применение должно учитывать версии агрегатов.

Каждый Gateway читает все партиции read_committed, без разделения по consumer group. Назначение партиций фиксируется при старте; изменение их числа требует перезапуска Projection Service и всех Gateway как части изменения топологии. Журнал в памяти ограничен 10000 сообщениями, 8 MiB и 15 минутами. При отсутствии диапазона выполняется чтение Kafka до захваченных концов, затем догоняется живой журнал. Одинаковые векторы разделяют одно историческое чтение. Одновременно допускается 4 разных чтения; завершённый результат можно повторно использовать в течение 2 секунд.

Историческое чтение ограничено 10000 исходными сообщениями, 4 MiB и 5 секундами после получения границ. Вектор должен точно покрывать текущие партиции; позиции вне retention, из будущего, токены старше 15 минут, старые события или превышение бюджета требуют ResyncRequired. Неполный диапазон не выдаётся как успешное восстановление. После ResyncRequired клиент получает новый согласованный REST-снимок. Старый токен прежней реализации требует одного нового снимка при обновлении.

## Оперативное состояние

`STREAM_LOCATION_STATUS` требует `location_status`, `filter.location_id` и токен соответствующего REST-снимка. После подписки передаётся свежий полный `GetLocationStatusResponse`; каждый следующий образ заменяет предыдущий целиком, включая удалённые ресурсы. Это актуальное состояние устройств, зон и коннекторов, а также качество, обслуживание и дежурство. Промежуточные образы могут объединяться; поток не является историей каждого изменения оборудования.

Gateway запрашивает Projection Service с исходным JWT. Запросы к одному объекту объединяются только при одинаковых тенанте, ролях и областях. Интервал между проходами - 50 мс; время запросов добавляется к интервалу. Истечение свежести, обслуживания или lease обнаруживается без новых Kafka-событий. При восстановлении старый образ не подтверждает online или actual. Gateway не строит отдельную модель оборудования. Число различных объектов и наборов прав влияет на нагрузку Projection Service.

## Ограничения и наблюдаемость

| Параметр `settings` | По умолчанию |
|---|---:|
| `realtime_max_connections` | 1024 TCP-соединения, включая REST и handshake |
| `realtime_max_subscriptions` | 16 на соединение |
| `realtime_queue_messages` | 1000 сообщений на соединение |
| `realtime_queue_bytes` | 4194304 байта на соединение |
| `realtime_total_queue_bytes` | 67108864 байта на процесс, включая текущие записи |

Срок записи - 2 секунды. При переполнении отправляется `REALTIME_SLOW_CONSUMER`, если транспорт ещё принимает данные, затем закрывается соединение. При блокированной записи соединение закрывается по сроку. Прекращение чтения Kafka или обработки оперативных образов снимает readiness, закрывает существующие WebSocket и отклоняет новые соединения до перезапуска процесса. Управляющие кадры ограничены 16 KiB и 100 кадрами/с с burst 200. Поддерживается `permessage-deflate` без сохранения контекста между сообщениями.

`psim_realtime_connections` показывает активные WebSocket, `psim_realtime_slow_consumers_total` - превышение очереди или срока записи. `psim_realtime_delivery_seconds` измеряет Kafka CreateTime -> постановка живого изменения в очереди; историческое восстановление и время отрисовки не входят. Панель API Gateway показывает соединения, задержку и отключения медленных клиентов.

## Проверка

```bash
task realtime:test
task realtime:bench
task realtime:sanitizers
task realtime:coverage
```

Проверка использует два Gateway, настоящие WSS/JWT, Kafka, PostgreSQL, Valkey и сервисы-владельцы. Каждому Gateway в тесте выделен предел памяти 1 GiB; для общего адреса нагрузочного клиента `ip_rate_per_second` и `ip_rate_burst` установлены в 10000. По 250 соединений на каждом узле получают 20 изменений с интервалом 200 мс: 10000 доставок без потерь и повторов. Задержка измеряется от `produced_at`, установленного нативным издателем непосредственно перед сериализацией и отправкой в Kafka, до разбора сообщения клиентом. Подготовка процесса и получение схемы выполняются до отметки; часы контейнеров общие. Затем второй узел останавливается, публикуются 5 событий инцидентов и изменение дежурства, и все 500 клиентов возобновляются на перезапущенном узле из Kafka: 3000 доставок из обоих топиков без нового снимка.

Обычный инцидент имеет короткий заголовок `Realtime verification`; проверка медленного получателя использует 64 сообщения с заголовком из 160000 ASCII-символов. Эти данные создаются в отдельном тестовом Compose-проекте.

Отдельно проверяются фильтры, несколько подписок, старый клиент, приватные варианты, авторизация через владельца, оперативный образ и истечение lease, смена прав, недопустимые позиции, JWT и получатель, переставший читать. Обычные сборки требуют p99 не выше 200 мс; инструментированные сборки проверяют корректность. Локальный профиль проверяет канал; полная нагрузка платформы LOAD-50K остаётся отдельной проверкой.

Артефакты: `build/realtime/<preset>/result.json`, журналы обоих Gateway и `peer-result.json`. Coverage дополнительно сохраняет проверки моделей консоли, Catalog, отчётности, браузерного M1 и модульные тесты.
