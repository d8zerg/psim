# Поставка двух топологий

Статус: Принято. Поставка использует одинаковые сервисы и контракты для одной машины и кластера. Различаются инвентарь, конфигурация инфраструктуры и число экземпляров. Измеренная производительность локального профиля принята для шага 9.1 в приведённых ниже границах проверки.

## Профили

| Профиль | Назначение |
|---|---|
| `deploy/topologies/single.json` | Одна машина Debian 13 x86_64 |
| `deploy/topologies/cluster.json` | Раздельные инфраструктурные, прикладные и наблюдающие узлы |
| `deploy/topologies/local-single.json` | Топология одной машины в одной локальной VM |
| `deploy/topologies/local-vm.json` | Кластер на трёх локальных VM |

Профили задают адреса, домены отказа, публичный адрес, VIP и интерфейс VRRP. Для локального кластера выделены три VM по 4 vCPU, 12 ГиБ RAM и 60 ГиБ диска. Одна физическая машина позволяет проверить выключение гостевой ОС и переключение процессов; независимость физических доменов отказа этим не подтверждается. Устройство стенда описано в [руководстве VM](local-vm-lab.md).

## Запуск локальной поставки

Команды выполняются из корня репозитория на Linux с нативным Docker Engine, Compose и доступным KVM.

```sh
task deploy:images
task deploy:vm:up TOPOLOGY=cluster
task deploy:vm:status
task deploy:vm:down
task deploy:vm:up TOPOLOGY=cluster
```

`up` формирует публичный комплект конфигурации, создаёт свежий материал стендовой PKI и учётных записей, запускает VM, устанавливает закреплённые пакеты Docker, переносит конфигурацию и образы, настраивает инфраструктуру, темы и ACL Kafka, схемы Registry и закрытый bucket. Завершение команды требует готовности всех прикладных экземпляров.

Registry, Keycloak, filer и S3 запускаются после проверки доступного для записи primary PostgreSQL и синхронных реплик. При первоначальной установке и возобновлении остановленного стенда эти процессы проходят запуск после проверки базы. Это исключает первоначальную инициализацию Registry до готовности PostgreSQL.

Консоль доступна по `https://localhost:8443`, Connector Gateway - по `localhost:7443`. Публичный CA для проверки HTTPS находится в `build/deployment/lab-cluster-ca.pem`. Закрытые ключи CA остаются на машине управления; в VM передаётся только материал её ролей.

Для перехода к другой топологии нужно удалить текущий стенд:

```sh
task deploy:vm:destroy
task deploy:vm:up TOPOLOGY=single
```

`down` сохраняет диски и идентификаторы. `destroy` удаляет собственные VM, диски, закрытый материал, узловые архивы и публичный комплект текущего стенда. Общие кеши базового образа и пакетов сохраняются. Чужие контейнеры и каталоги не удаляются. Изменение инвентаря, публичного комплекта или идентификаторов образов требует пересоздания; `up` не заменяет существующую установку другим комплектом.

Стендовые сертификаты действуют два дня. Стендовая выдача отделена от производственной внешней PKI. Для долговременной эксплуатации нужен внешний процесс выдачи и продления.

После готовности можно создать первоначального администратора:

```sh
task deploy:account BUNDLE=build/deployment/lab-cluster PRIVATE=.cache/deployment/lab-cluster/material USERNAME=platform-admin
```

Команда запрашивает временный пароль; первый вход требует его смены и TOTP. Внешняя выдача, первоначальное доверие, регистрация и продление описаны в [регламенте PKI и Keycloak](deployment-pki.md).

## Формы запуска приложений

Инфраструктура использует Docker Compose в обеих топологиях. Прикладные процессы запускаются контейнерами или из Debian-пакетов под systemd; конфигурация, UID, секреты, порты и каталоги данных сохраняются.

```sh
task release:package
task deploy:runtime RUNTIME=systemd
task deploy:flow
task deploy:runtime RUNTIME=containers
```

`psim-taxonomy` предоставляет общий файл таксономии; пакеты потребителей зависят от той же версии. Переключение останавливает предыдущую форму запуска и требует готовности новой. Удаление всего локального стенда выполняется через фабрику VM. Поддержка инфраструктуры без контейнеров в этот комплект не входит.

## Повторяемые проверки

| Команда | Проверяемое свойство |
|---|---|
| `task vm:test` | Жизненный цикл KVM, изоляция ресурсов, выключение и собственное удаление |
| `task deploy:check` | Четыре профиля, Compose, Helm, UID и изоляция материала экземпляров |
| `task deploy:flow` | Свежий коннектор, план, нормализованная история, инцидент и общая консоль |
| `task deploy:gateway:bench` | Ввод 400 000 событий через два шлюза с барьером 50 000 событий/с и сверкой Kafka; прочие приложения временно остановлены |
| `task deploy:gateway:failover` | Потеря активного процесса, переключение SDK и сверка 1 000 событий |
| `task deploy:postgres:qualify` | Выключение VM с primary, RTO записи и RPO подтверждённых транзакций |
| `task deploy:console:qualify` | Приостановка writer, передача роли и fencing возобновлённого процесса |
| `task deploy:storage:qualify` | Чтение планов при семи отказах процессов, восстановление, новая версия и запрет анонимного чтения |
| `task deploy:operators:qualify` | SHA-256 и рендеринг закреплённых операторов |

Нагрузочная проверка шлюза и приостановка writer используют контейнерную форму приложений. Проверка хранилища использует контейнерную инфраструктуру при обеих формах приложений. Проверки используют собственную установку и свежие удостоверения; их операции сериализуются с `up`, `down`, `destroy` и переключением форм запуска.

## Изоляция ролей

Каждая прикладная и инфраструктурная роль получает отдельный числовой UID, каталог материала `0700` и файлы `0400`. Образы работают без root, с корневой файловой системой только для чтения и без capabilities. HAProxy получает только право привязки порта; VRRP работает отдельным systemd-процессом с ограниченными сетевыми capabilities. Аппаратный watchdog PostgreSQL доступен только его роли.

Kafka использует mTLS, явные ACL тем, групп и транзакционных идентификаторов; автоматическое создание тем запрещено. PostgreSQL предоставляет прикладным ролям собственные схемы без права создания баз и ролей. Журнал загрузчиков ClickHouse разделён политиками RLS. Для ClickHouse отделены роли записи и чтения; Valkey разделяет прикладные ACL, репликацию и управление Sentinel. Registry запрещает прикладным клиентам менять схемы. S3 предоставляет Catalog доступ только к bucket планов; анонимный доступ запрещён.

Keycloak выдаёт токены с аудиторией `psim` и аудиториями серверов ресурсов. Каждый сервис выполняет introspection со своей учётной записью. Проверка аудитории при introspection сохраняется. Секреты, токены и ключи не передаются аргументами команд и не включаются в Git.

## Объём проверок

Проверены создание и удаление VM, готовность 26 прикладных экземпляров кластера и публичный HTTPS с CA и TLS 1.3. Проверка ввода на двух шлюзах подтвердила 296 905 событий/с: 400 000 подтверждённых событий за 1,347 с, все найдены в Kafka. Для этого прогона прочие прикладные сервисы остановлены; граница измерения - получение пакета шлюзом -> подтверждение всех ISR Kafka. Время подготовки клиентов и завершения транспортов исключено. После проверки сервисы восстановлены с ожиданием готовности всех 26 экземпляров. Устойчивость всего предметного конвейера в течение 24 часов этим прогоном не подтверждается.

Два прогона с работающими фоновыми приложениями и остановленными только normalizer дали 32 850 и 38 100 событий/с при полной сверке Kafka. Это ниже 50 000 событий/с. На совмещённом локальном профиле L-06 проверяет отдельно ввод шлюз -> Kafka; совместная производительность приложений и длительная нагрузка требуют отдельной квалификации на эталонной конфигурации.

Нагрузочная синтетика L-06 не имеет предметного каталога источников и после возврата normalizer обрабатывается через DLQ. Накопленная очередь на совмещённом профиле может задержать следующее предметное событие: один сквозной прогон после нагрузки превысил свой предел 90 с. Перед отдельной функциональной проверкой следует дождаться обработки очереди. Этот предел не используется как доказательство задержек конвейера под нагрузкой. Регистрация в квалификационном клиенте повторяет только временные ошибки с сохранением идентификатора запроса.

При принудительном завершении активного шлюза с отключённым автоматическим перезапуском SDK перешёл на другую реплику: 1 000 подтверждений, 0 отказов, 0 ожидающих событий; сверка Kafka не обнаружила потерь. При выключении VM с primary PostgreSQL запись возобновилась через 31,54 с; сохранены все 11 подтверждённых записей. Переключение writer общей модели консоли после приостановки процесса заняло 17,522 с; возобновлённый процесс уступил роль.

Сквозной предметный сценарий прошёл на кластере в контейнерах и под systemd. При поочерёдной остановке трёх volume, двух filer и двух S3 gateway планы сохранили исходный SHA-256. После возврата процессов подтверждены не менее двух копий каждого из 12 томов в разных rack, загрузка следующей версии и HTTP 403 при анонимном запросе существующего объекта. Это минимальная проверка файлов для установки; расширенный C-15 включает дополнительные отказы и запись во время нарушения доступности.

Проверены 300 модульных тестов и 12 тестов runtime под ASan/UBSan и TSan. Фатальная ошибка транзакционного producer завершает процесс для перезапуска supervisor; реальный fencing normalizer проверен на кластере. Первоначальная внешняя PKI прошла путь CSR -> внешняя подпись -> проверка -> узловой архив. Создание учётной записи проверено с обязательной сменой пароля и настройкой TOTP.

Чистая установка одной машины прошла сквозной сценарий в контейнерах и под systemd. Проверены остановка и возобновление с сохранением пакетов и данных, возврат к контейнерам и повторный сквозной сценарий. Пересозданный кластер прошёл проверки ввода, отказов, повторного `up`, остановки, холодного возобновления и завершающий сквозной сценарий. Ранее созданный план сохранил контрольную сумму. Установщик применяет права для обоих интерфейсов watchdog; правило udev сохраняет владельца после перезагрузки. Отчёты - `build/deployment/canonical-qualification.json` и `build/deployment/watchdog-lifecycle.json`. Журнал состояния - [progress.md](../progress.md).

## Kubernetes

[Helm-чарт](../../deploy/helm/psim-platform/Chart.yaml) включает backend, веб-клиент и публичный HAProxy. Он принимает файловую конфигурацию и отдельный Secret для каждого экземпляра. Init container копирует projected Secret в принадлежащие пользователю файлы `0400` в памяти. Процессы работают без root и повышения привилегий; предусмотрены health, штатный `SIGTERM`, постоянные тома, размещение реплик на разных узлах и PodDisruptionBudget. Право привязки привилегированного порта разрешено только публичному proxy. Образы задаются по digest.

`tools/deploy/helm.py` формирует значения из публичного комплекта и локальных OCI-образов. Перед установкой задать целевые DNS и issuer, адреса инфраструктуры, внешние Secrets и подходящий класс хранения. Внешнее изменение Secret требует перезапуска соответствующих StatefulSet, чтобы init container подготовил новый материал. Статическая проверка использует временные фиктивные digest только для рендеринга; они удаляются после проверки.

[Каталог операторов](../../deploy/operators/operators.json) закрепляет версии и SHA-256 чартов Strimzi, Zalando Postgres Operator, Altinity ClickHouse Operator и SeaweedFS Operator. Проверены загрузка по контрольной сумме и рендеринг их ресурсов. Для PostgreSQL оператор использует Patroni; параметры его Kubernetes DCS отличаются от etcd в VM-поставке. Адреса инфраструктуры, PKI, ACL и секреты требуют настройки под целевую среду.

Проверка чартов не включает живую установку Kubernetes, переключение его хранилищ и квалификацию его инфраструктуры. Собственный оператор PSIM не создаётся.
