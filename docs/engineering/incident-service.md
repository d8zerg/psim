# Incident Service

Сервис реализует шаг 5.3; решения - [ADR-020](../adr/0020-authorization-model.md), [ADR-027](../adr/0027-incident-states.md) и [ADR-053](../adr/0053-incident-service.md).

## Запуск и конфигурация

Пакет и образ `psim-platform/psim-incident-service` используют общий runtime. Для обработки нужны Kafka, Schema Registry и PostgreSQL; REST работает по HTTPS с проверкой JWT. Пример локальной конфигурации - [incident-service.yaml](../../deploy/local/config/event-flow/incident-service.yaml). Параметры `tls_certificate_file`, `tls_private_key_file`, `tls_ca_file` и `jwks_ca_file` задают доверие. Открытые соединения разрешаются только явным `allow_plaintext` в изолированном окружении.

Для проверки получателей задаются `directory_base`, `directory_client`, `directory_roles_client` (UUID клиента ролей `psim` в Keycloak) и `directory_secret_file` с правами 0400 пользователя сервиса. База указывает на Keycloak с realm `psim`; клиент имеет `realm-management/view-users` и `view-clients` без прав изменения. Пользователь содержит атрибуты `psim_tenant` (одно значение) и `psim_scopes` (список областей), согласованные с выдаваемым JWT. Запросы не принимают роли или области получателя из браузера. Отсутствие настройки или отказ Keycloak запрещает назначение и передачу, обработка сигналов продолжается.

## REST и конкурентность

Публичные пути - `/v1/incidents`, карточка, timeline, signals, команды acknowledge, start-work, assign, set-priority, resolve, reopen и close, коллекции comments и links; типы - `/v1/incident-types`. JSON соответствует опубликованным Protobuf и OpenAPI. POST требует UUID Idempotency-Key; изменение существующего агрегата - If-Match с версией в кавычках. Повтор с тем же содержимым возвращает прежний результат, конфликт версии возвращает 412. Поля, которых нет в контракте, отклоняются.

Пакет `/v1/incidents:transfer` принимает до 100 items. Каждый содержит incidentId, expectedVersion, recipientId и comment; для подтверждения используются transferId и expectedVersion, а JWT принадлежит получателю. Ответ results сохраняет порядок и содержит incident или errorCode для каждой строки. Пакет не является одной транзакцией. До подтверждения отвечает прежний оператор; каждое действие сохраняется в timeline и аудите.

Просмотр и поиск фильтруются по тенанту, площадке и зоне. Администратор без дополнительной роли operator/supervisor не обрабатывает инциденты. Присутствие получателя в консоли не проверяется. Назначение разрешено старшему смены либо оператору себе; передача другому оператору требует подтверждения.

## Долговечность

Сигнал, переход, timeline, аудит и outbox используют транзакции PostgreSQL. Kafka подтверждается после фиксации агрегата, outbox публикуется отдельно. Повторная публикация событий возможна; их идентификатор и версия позволяют потребителю исключить повторный эффект. Полный список сигналов доступен постранично; preview в incident ограничен 1000 элементами и сопровождается счётчиком и признаком усечения.

События `RunUpdated` из `psim.response.events.v1` обновляют обязательные шаги и версию запуска; устаревший снимок игнорируется. Уровень эскалации меняется отдельно от состояния.

Изменение типа не меняет уже созданные инциденты. Автоматическое закрытие переживает перезапуск и выполняется одним из экземпляров. Истечение окна группировки не закрывает прежний инцидент и не сбрасывает его ответственность.

## Проверки

```sh
task incidents:test
task incidents:bench
task incidents:sanitizers
task incidents:coverage
task incidents:sim
```

Профиль и отчёты сохраняются в `build/incidents/<preset>/`. Сообщения сигналов обрабатываются по одному: ожидание предыдущих транзакций в уже прочитанном пакете не скрывается за замером. Метрика `psim_incident_signal_seconds` измеряет длительность обработки сигнала до завершения транзакции PostgreSQL; ожидание Kafka и публикация outbox измеряются отдельно. Короткий локальный замер не подтверждает длительные кластерные SLO.
