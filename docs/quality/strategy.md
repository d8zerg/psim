The `task docs:verification` task verifies coverage of each objective G-01-G-19 and each S1-S13 scenario using either automatic gates or manual procedures. Automatic methods are required for SLOs. Repeated IDs, unknown objectives, scenarios, and methods are rejected.

---

## 1. Principles

1. **Evidence, not declaration.** Each objective has a measurable threshold, method, and where the threshold is automatically checked.
2. **Fast tests first.** The maximum number of checks is in fast levels: domain core, properties, simulation. Higher levels (cluster, 24 hours) confirm what cannot be verified earlier.
3. **Determinism.** Domain core and pipeline are tested deterministically (ADR-016, ADR-044); any found errors are reproduced by seed.
4. **One task interface.** All checks are Task tasks (ADR-030); CI calls the same tasks as developers.
5. **Gate, not report.** Violation of thresholds blocks merging or release; exceptions are clearly recorded in the registry as known limitations.
6. **Observability as verification tool.** Load and chaos tests evaluate results using the same metrics and tracing as production.

## 2. Testing Levels

| Level | What is tested | Tools | Where performed | Speed |
|---|---|---|---|---|
| Unit | Domain core and pure functions | GoogleTest, GMock | PR | seconds |
| Property-based | Invariants of aggregates and state models on random command sequences | RapidCheck | PR | seconds |
| Component | Services with real adapters against Kafka, PostgreSQL, Redis, ClickHouse containers | GoogleTest + Docker Compose | PR | minutes |
| Contract | Contract compatibility; OpenAPI compliance; connector conformance (conformance kit) | buf, Schema Registry, Schemathesis, conformance kit | PR | minutes |
| Simulation | Pipeline in one process with Kafka and storage emulation, with fault injection and controlled time | Deterministic test `libs/sim` | Manual: `sim:short` (200), `sim:long` (10,000), ADR-044 | minutes - hours |
| Integration | End-to-end flow in Docker Compose: from simulator to console | Task + Compose + API tests | PR (smoke), night | minutes |
| E2E UI | Operator and administrator scenarios in browser | Playwright | night, release | minutes |
| Benchmark | Throughput and latency of hot components against baseline | Google Benchmark | PR (affected), night | minutes |
| Load | Throughput and SLO delay under load | Simulator (load generator), Prometheus metrics | night (simplified profile), release (full) | hours |
| Soak | 24-hour stability: leaks, lag growth, degradation | Simulator, metrics | release | 24 hours |
| Chaos | Behavior during failures: losses, duplicates, RTO, RPO | Toxiproxy, process and node stops, reconciliation | night (basic set), release (full) | hours |
| Security | SAST, dependencies and images, DAST, fuzzing, TLS, authorization checks | clang-tidy, Trivy, OWASP ZAP, libFuzzer, testssl.sh | PR (SAST, dependencies), night, release | minutes - 24 hours |
| Fitness functions | Architectural rules | Scripts `tools/`, Task tasks | PR | seconds |
| Manual | What cannot be automated: installation by external engineers, recovery exercises, penetration tests | Procedures | release | days |

### 2.1 Distribution of tests

Reference for the number of tests: unit and property-based - majority; component and contract - dozens per service; simulation - failure scenarios for each data stream; integration and E2E - by acceptance scenarios; load, soak, chaos - fixed set of experiments in [verification.yaml](verification.yaml).

### 2.2 Testing of domain core

- Each invariant from [aggregates.md](../domain/aggregates.md) is a separate test and, where applicable, a property: “for any valid command sequence, the invariant is satisfied.”
- State models ([state-models.md](../domain/state-models.md)) are thoroughly tested: each transition is allowed or rejected with expected error code.
- Time and identifiers are through ports `Clock` and `IdGenerator`; in tests, they are deterministic.

## 3. Test Environments

| Environment | Composition | Purpose |
|---|---|---|
| `E-DEV` | Developer's Linux machine: native Docker Engine and Docker Compose plugin, Kafka 1 broker | Unit, component, integration, debugging |
| `E-CI` | Developer's Linux test environment with native Docker Engine, where pipelines `task ci`, `task ci:nightly`, `task release` ([ADR-034](../adr/0034-local-ci-and-supply-chain.md)) run; same Compose | Gates for PRs and night runs in simplified profile |
| `E-LOCAL` | Standard “one-machine” server ([scaling.md](../architecture/scaling.md#54-standard-test-environments)) | Functional E2E, load of one-machine profile |
| `E-CLUSTER` | Standard cluster on VM: 3 infrastructure nodes, 2 application nodes, monitoring node | Full load, soak, chaos, updates |

For qualification of delivery, [local E-CLUSTER profile](../engineering/deployment-topologies.md) is used: three KVM guests with 4 vCPU, 12 GiB RAM and 60 GiB disk on one physical Linux host; roles are combined. It tests L-06 input and failures of guest OS and processes. Results belong to this profile and do not replace testing of the standard hardware configuration, independent physical failure domains, and long-term load of the entire pipeline.

Load profiles: `LOAD-50K` ([acceptance-spec.md](../product/acceptance-spec.md#general-conditions)), `LOAD-10K` for one machine, `LOAD-5K` for night runs in CI.

## 4. Gates

| Gate | When | What blocks | Composition |
|---|---|---|---|
| **PR** | Each commit: `task ci` before the commit ([ADR-036](../adr/0036-no-git-hooks.md)); change range - [ADR-034](../adr/0034-local-ci-and-supply-chain.md) | Commit and push in `master` | `task check`; build with `-Werror`; clang-tidy; unit, property, component, contract; ASan+UBSan and TSan sanitizers; coverage; benchmarks for affected components (regression > 5%); smoke integration; fitness functions; SAST and dependency checks |
| **Nightly** | Daily on `master` (`task ci:nightly`, full range) | Next release, creates a task when down | Integration and E2E; load `LOAD-5K`/`LOAD-10K`; basic chaos set; one hour of fuzzing per target; image scanning |
| **Release** | Candidate for release (`task release`) | Release | Full load `LOAD-50K`; peak ×1.5; soak 24 hours; full chaos set on `E-CLUSTER`; N -> N+1 updates and rollbacks; DAST; 24 hours of fuzzing; TLS checks; manual procedures; SBOM and signatures |

In CI, 10 minutes of parser and rule validator fuzzing must complete without crashes or sanitizer errors. A full execution of each target for 24 hours is required for release qualification.

Rule: A red gate PR cannot be passed; a red nightly block release until correction or explicit note of known limitation.

According to [ADR-044](../adr/0044-deterministic-simulation.md), simulation starts only manually with separate tasks `sim:*` and `correlation:sim`, without connecting to CI and release gates. TS-07 and TS-08 have a mode `on-demand`: the command automatically evaluates the result, and the engineer executes the launch. Oracles separately check the reference delivery chain and signals of the actual correlation engine. Incident Service unit and integration tests verify domain incident invariants.

## 5. Unstable Tests

- A test that fails but passes without code changes is considered unstable and marked within a day.
- Unstable tests are corrected or removed within 5 working days; quarantine does not exceed this period and is visible in the CI report.
- Tests do not use `sleep` for synchronization; waiting - according to the deadline condition.
- Distributed scenarios without determinism are transferred to simulation, where they are deterministic.

## 6. Coverage

| Range | Threshold | Measurement |
|---|---|---|
| Domain core (`libs/domain/*`) | ≥ 90% lines, ≥ 80% branches | llvm-cov for unit and property tests |
| Infrastructure code (`libs/platform/*`, `services/*/adapters`) | ≥ 75% lines | llvm-cov for unit, component, and integration |
| Web client | ≥ 80% lines for logic (stores, API client, realtime protocol) | Vitest coverage |

Coverage is a necessary but not sufficient condition: domain invariants are additionally checked with properties and simulation.

## 7. Test Data

- Generated by the simulator and fixtures from code; personal data in tests is only synthetic.
- Each acceptance scenario has an object fixture (site, building, zone, device), rules, and response scenarios; fixtures are versioned in the repository.
- Load profiles are described declaratively (number of devices, distribution by sites, intensity by event type, peaks) and reproducible by seed.

## 8. Reporting

- Each CI run publishes: test results, coverage, benchmarks against baseline, reconciliation and latency reports for load and chaos tests.
- Release report collects status per target [verification-matrix.md](verification-matrix.md): confirmed or known limitation with order of removal. Unperformed checks are explicitly indicated.
